# Capture Intent

把零散的原始材料收敛为忠于发起人表达、可由下一阶段直接读取的 `intent.md` 草稿。Skill 的输出仍是草稿；只有发起人纠正理解偏差、产品负责人接受后，它才成为正式阶段产物。

## 边界

- 保留原始问题、期望结果和限制条件，不把推测写成事实或已确认决定。
- 描述需要达成的结果，不扩展成需求设计、技术方案、任务拆解或实现计划。
- 不替发起人补充业务决定，不替产品负责人接受、拒绝、排期或定优先级。
- 不负责采集监控指标、执行事故响应、提交版本控制或启动下一阶段；仅整理用户已经提供或明确授权读取的材料。
- 用户给出组织模板时优先遵循该模板，同时保留本 Skill 要求的核心信息。

## 整理流程

1. 完整读取用户指定的讨论、工单、事故记录或其他来源。记录可追溯标识，例如文件路径、工单号、链接、时间戳或事件 ID；没有的信息标为 `待确认`，不要编造。
2. 区分来源中已经陈述的事实、明确要求、约束、范围外内容和待确认事项。只有来源明确提出时，才保留具体方案；将它标为发起人的已知偏好，不把它升级为必要实现。
3. 仅对会显著改变问题、结果、边界或受影响对象的缺失信息提出澄清问题。能够继续时先生成有用草稿，并把缺口放入“未决问题”，不要为了补齐所有字段阻塞输出。
4. 使用 [assets/intent.md.tpl](assets/intent.md.tpl) 生成草稿。若用户要求写入文件，先遵循目标仓库已有位置、命名与文档规范；未指定写入时直接返回 Markdown 草稿。
5. 输出后列出最需要发起人确认的问题，并明确说明草稿尚未获得产品负责人接受。除非用户另行要求，不执行提交、审批或后续 `spec.md` 生成。

## 内容要求

每份草稿至少表达以下信息；未知项写 `待确认`，不要静默省略。

- 标题、来源、发起人、记录时间和草稿状态。
- 当前问题及其可核验表现。保留能解释问题来源的关键原话、数据或事实，但不要虚构引语。
- 期望结果。优先描述用户或业务状态的变化，避免提前规定实现方式。
- 受影响的用户、团队、流程与系统；尚不确定时区分已知和待确认部分。
- 已知约束，包括业务、时间、数据、政策、兼容性或权限限制。
- 明确的范围外内容。来源未说明时写 `待确认`。
- 判断问题得到改善的成功信号。没有可量化标准时忠实记录定性结果，并将量化方式列为未决问题。
- 未决问题。问题应指向需要发起人、产品负责人或相关负责人作出的决定。

## 事故与维护来源

当输入来自控制带越界、缺陷、安全发现、频道消息或事故诊断时，在核心结构之外补充：

- 触发时间和触发来源。
- 异常证据、指标、日志或复现信息。
- 已确认的影响范围。
- 已经执行的动作及其结果。
- 已确认事实与诊断假设之间的区别。

不要自行判定根因、严重程度、修复优先级或响应动作。来源中已有这些判断时，注明判断者或来源。

## 完成检查

交付前检查：

- 每个关键结论都能追溯到输入，或明确标为 `待确认` / `假设`。
- 问题、结果、受影响对象、约束、范围外内容、成功信号和未决问题均已覆盖。
- 没有把偏好改写成硬性约束，没有悄悄引入用户未选择的方案。
- 没有混入 `spec.md` 才应决定的功能细节、系统设计和验收方案。
- 状态仍为草稿，人工纠正与产品负责人接受的关卡清晰可见。
