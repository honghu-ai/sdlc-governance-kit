# Security Policy

把组织已经确定的通用安全政策应用到设计阶段，使安全约束在工程计划形成前可追溯、可验收。输出只覆盖安全相关部分，不拥有完整 `spec.md`，也不代表安全负责人批准。

## 所需输入

- `intent.md`、变更范围和正在编写或审核的 `spec.md`（如有）。
- 系统与信任边界、数据类型和分类、用户与服务身份、外部依赖及数据流。
- 当前权威组织安全政策，以及版本或生效日期。
- 已有风险接受、例外、威胁分析或安全负责人决定记录。

缺少安全政策或系统背景时，可以识别输入缺口和需要关注的边界，但不得用通用最佳实践冒充组织要求，也不得虚构现有架构、数据分类或正式风险等级。

## 适用范围

按变更实际涉及的内容检查：

- 身份认证、授权、权限边界和最小权限要求。
- 数据分类、收集、传输、存储、删除和敏感信息暴露。
- 密钥、令牌、证书和其他秘密的生命周期与访问边界。
- 第三方依赖、软件供应链、构建来源和更新约束。
- 网络访问、跨系统通信、入口、出口和信任边界。
- 日志、审计、安全事件证据和敏感信息记录限制。
- 文件上传、后台任务、消息队列及其他非 API 场景的威胁关注点。
- 政策例外、风险接受和必须升级给安全负责人的条件。

涉及外部 API 时，只输出通用安全政策约束，并把端点认证、输入校验、审计事件、PII 和实现检查路由给 `secure-api-review`。本 Skill 不替代专项 API 安全验证。

## 工作模式

### 为规范提供内容

1. 根据系统、数据和信任边界确定适用政策，并记录权威来源与触发事实。
2. 将适用规则转换为安全约束和可观察的验收条件；明确所需证据，但不指定文件、类或实现顺序。
3. 列出与当前边界相关的威胁关注点、政策冲突、待验证假设和需要安全负责人判断的问题。
4. 只输出可写入 `spec.md` 安全、非功能、验收和风险章节的内容，不改写其他需求。

### 审核规范中的安全内容

1. 对照权威政策和已知边界核对安全约束、验收证据、例外及升级条件。
2. 报告遗漏、错误转述、不可验证条件、边界不清和无依据的风险接受，并提供规范与政策证据位置。
3. 区分应在 `spec.md` 补充的结果约束、应在 `plan.md` 决定的实现方式及需要确定性控制承接的强制规则。
4. 只给出安全审核建议，不宣称实现安全、规范获批或风险已被接受。

## 输出格式

1. **安全适用性摘要**：系统、数据、信任边界、适用政策、来源和未知项。
2. **安全约束与验收条件**：每项包含政策依据、约束、可观察结果、所需证据和责任角色。
3. **威胁关注点与缺口**：说明触发事实、潜在影响、缺少的信息或验证，不把可能性写成已确认漏洞。
4. **例外与升级事项**：列出风险接受或例外状态、负责人、升级条件及对规范批准的影响。
5. **专项检查路由**：涉及外部 API 时列出需要交给 `secure-api-review` 的内容。

## 完成检查

- 身份与授权、数据、密钥、依赖、网络、日志和供应链已按适用范围核对。
- 每项组织安全要求都能追溯到权威输入，或明确标为无法判断。
- 验收条件描述结果和证据，没有越过 `spec.md` 与 `plan.md` 的边界。
- 没有生成整份 `spec.md`，没有伪造政策、架构事实、风险等级、例外或批准。
- API 专项问题已正确路由，没有用通用安全政策替代实现级检查。
