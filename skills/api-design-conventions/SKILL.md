# API Design Conventions

把组织的 API 设计约定转换为规范可以引用和验收的契约约束，并检查契约变更是否保持兼容。输出只覆盖 API 设计部分，不拥有完整 `spec.md`，也不代表 API 负责人批准。

## 所需输入

- `intent.md` 或变更说明，以及正在编写或审核的 `spec.md`（如有）。
- 权威 API 设计规范及其版本，例如命名、版本策略、错误模型、分页与弃用政策。
- 现有契约（OpenAPI、Protobuf、GraphQL Schema 等）与拟议契约或接口说明；已知调用方清单（如有）。

没有组织 API 规范时，可以按通用 REST/RPC 惯例给出建议，但必须标为 `建议（非组织规范）`，并列出缺少的来源和负责人。

## 检查维度

- 资源与路径：命名风格、复数、层级深度、动作型端点是否有依据。
- 方法与语义：HTTP 方法与状态码使用是否一致；写操作的幂等与重试语义。
- 字段与 Schema：命名风格、类型、必填与可空、枚举扩展方式、时间与金额格式。
- 集合接口：分页方式、排序、过滤、上限与默认值。
- 错误格式：统一错误结构、错误码、可本地化消息、与状态码的对应。
- 版本与兼容：版本策略；删除或重命名字段、收紧校验、改变默认值、改变语义均视为破坏性变更。
- 弃用：弃用标注、公告方式、迁移期限与负责人。

认证、授权、输入校验、审计和 PII 等安全专项交给 `$secure-api-review`；通用安全政策由 `$security-policy` 提供。

## 工作模式

### 为规范提供契约约束

1. 列出本次变更涉及的接口，记录依据的 API 规范来源与版本。
2. 按检查维度为每个接口写出必须满足的约束和可观察的验收条件，不预先选择框架或实现结构。
3. 对照现有契约标出新增、修改与删除项，并判断兼容性。
4. 将破坏性变更、规范冲突和未决问题列给 API 负责人，不自行裁定例外。

### 审核规范或契约文件

1. 读取 `spec.md` 中的 API 章节和契约文件；能取得旧版契约时做差异比较。
2. 按“严重 / 重要 / 建议”报告问题：未声明的破坏性变更为严重；缺少错误格式、分页或幂等定义为重要。
3. 每项问题包含证据位置、违反的规范条目、对调用方的影响和建议处理方式。
4. 只给出审核建议，不把自动检查结果写成批准。

## 输出格式

1. **适用性摘要**：涉及接口、依据规范与版本、契约来源。
2. **契约约束与验收条件**：按接口列出约束、规范来源和可观察结果。
3. **兼容性结论**：新增、非破坏性修改、破坏性修改清单及迁移要求。
4. **问题与待决定事项**：分级发现、证据、影响、负责人。

## 完成检查

- 每项约束能追溯到组织 API 规范，或明确标为非组织规范建议。
- 所有删除、重命名、收紧和语义变化都被识别为破坏性变更并给出迁移要求。
- 没有编写实现代码、没有替代安全专项检查、没有伪造批准或例外。
