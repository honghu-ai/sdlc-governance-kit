# Compliance Policy

把当前可得的权威合规要求转换为规范可以追溯和验收的领域内容。输出只覆盖合规部分，不拥有完整 `spec.md`，也不是法律意见或正式合规批准。

## 所需输入

- `intent.md`、变更范围和正在编写或审核的 `spec.md`（如有）。
- 涉及的用户、地区、数据类型、业务流程、渠道和系统边界。
- 权威法律、监管、行业或组织政策材料，以及版本或生效日期。
- 已有批准、豁免、例外和负责人决定记录。

没有权威材料时，不得用行业惯例或模型常识代替组织政策。应报告来源缺口，并将相应适用性和义务标为 `待合规负责人确认`。

## 适用范围

根据输入中的地区、主体、数据、流程和渠道判断规则是否适用，重点覆盖：

- 政策来源、适用范围、触发条件、版本和生效时间。
- 数据收集、使用、共享、保留、删除和记录义务。
- 审计、通知、披露、同意或其他政策明确要求的证据。
- 批准角色、职责分离、例外流程、期限和复审要求。
- 多项要求之间的冲突及必须由合规负责人裁决的问题。

不自行判断法律管辖、创建法律义务或把安全最佳实践写成合规规则。安全、品牌、UX 和 API 领域问题应交给对应 Skill 或负责人。

## 工作模式

### 为规范提供内容

1. 建立适用性清单，记录规则、触发事实、权威来源、适用结论和负责人。
2. 将适用义务转换为规范约束及可验证证据，保留原规则中的条件、例外和时限。
3. 记录政策冲突、无法判断的适用性、缺少的批准和仍需人工裁决的问题。
4. 只输出可写入 `spec.md` 合规章节、验收条件和风险记录的内容，不改写其他需求。

### 审核规范中的合规内容

1. 对照权威材料核对“来源与适用范围 → 合规义务 → 验收证据 → 负责人或例外流程”的链路。
2. 分别报告缺失来源、错误转述、证据缺口、政策冲突和无依据例外，提供政策与规范证据位置。
3. 区分规范必须补充的内容、后续确定性验证应提供的证据和必须由合规负责人决定的事项。
4. 只给出审核建议，不宣称规范或实现已合规、违规、批准或豁免。

## 输出格式

1. **适用性摘要**：规则、适用 / 不适用 / 待确认、触发事实、权威来源和负责人。
2. **合规义务与证据**：每项包含政策依据、规范约束、验收证据和责任角色。
3. **冲突与例外**：列出冲突规则、影响、已有依据、状态和待裁决事项。
4. **待人工决定**：列出缺少的信息或决定、所需负责人及其对规范批准或进入计划阶段的影响。

## 完成检查

- 每项适用结论和义务都能追溯到权威输入，或明确标为无法判断。
- 数据保留、审计证据、批准角色和例外流程已按适用范围核对。
- 义务与验收证据之间的缺口已显式记录。
- 没有生成整份 `spec.md`，没有创造法律结论、政策、豁免或批准状态。
