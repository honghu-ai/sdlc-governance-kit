# UX Standards

把组织已经确定的体验标准转换为规范可以引用和验收的领域内容。输出只覆盖用户流程、界面状态与可访问性相关部分，不拥有完整 `spec.md`，也不代表设计负责人批准。

## 所需输入

- `intent.md` 或变更说明，以及正在编写或审核的 `spec.md`（如有）。
- 权威 UX 材料：设计系统、交互规范、可访问性标准（例如组织采用的 WCAG 级别）及其版本或生效日期。
- 原型、线框、现有页面截图或流程说明；已有的设计例外和负责人决定。

没有权威 UX 材料时，可以指出通用可用性风险，但必须标为 `建议（非组织标准）`，并列出缺少的来源和负责人，不得冒充组织规则。

## 适用范围

当变更新增或修改页面、组件、交互流程、表单、通知、引导、错误提示或可访问性相关行为时使用。按实际涉及内容检查：

- 用户流程：入口、主路径、分支、返回与取消、中断后恢复、跨设备或跨渠道衔接。
- 界面状态：加载、空、部分数据、错误、成功、无权限、离线或超时状态是否都有定义。
- 可访问性：键盘操作、焦点顺序、可读名称、对比度、动效与时间限制、屏幕阅读器提示，以组织采用的标准级别为准。
- 文案与反馈：错误信息是否可理解、可操作；破坏性操作是否有确认与撤销。
- 设计系统一致性：是否复用现有组件与模式，偏离时是否有依据。

品牌视觉与语气交给 `$brand-guidelines`；产品范围、业务规则和技术实现不在本 Skill 决定范围内，只路由给对应负责人。

## 工作模式

### 为规范提供内容

1. 根据原型和变更范围列出受影响的流程与界面，记录所依据的 UX 标准来源与版本。
2. 为每个流程写出主路径与关键分支，为每个界面列出必须定义的状态。
3. 将适用的可访问性与交互规则转换为可观察的验收条件，不自行提高或降低标准级别。
4. 记录与设计系统的偏离、标准之间的冲突和仍需设计负责人决定的问题。
5. 只输出可写入 `spec.md` 体验与设计章节的内容，不改写其他需求。

### 审核规范中的 UX 内容

1. 对照权威材料检查 `spec.md` 中的流程、界面状态、可访问性要求和验收条件。
2. 报告缺失状态、不可验证条件、与标准不符之处和冲突，附规范与标准的证据位置。
3. 按“严重 / 重要 / 建议”分级：阻断任务完成或排除辅助技术用户为严重；缺少关键状态或验收条件为重要。
4. 区分需要修订规范的问题、应在可用性测试或可访问性测试中验证的事项和必须由设计负责人裁决的事项。

## 输出格式

1. **适用性摘要**：受影响的流程与界面、依据的标准与版本、适用结论。
2. **用户流程**：主路径、分支、异常与恢复，每项注明来源。
3. **界面状态清单**：每个界面需定义的状态及期望表现；不适用的状态写明原因。
4. **可访问性与体验验收条件**：可观察结果、所依据规则和验证方式。
5. **问题、冲突与待决定事项**：证据、影响、建议处理方式与负责人。

## 完成检查

- 每项要求能追溯到权威 UX 材料，或明确标为非组织标准的建议。
- 关键界面的加载、空、错误、成功和无权限状态均已覆盖或说明不适用。
- 可访问性条件以组织采用的标准级别为准，且可验证。
- 没有生成整份 `spec.md`，没有规定组件实现代码，没有伪造设计批准或例外。
