# SDLC Scaffold

建立可重复运行、不会覆盖团队内容的代码库级治理骨架。它只负责长期生效的仓库结构和规则入口，不负责启动某一项变更或越过人工批准关卡。

## 输入与模式

开始前确认目标代码库，并根据请求选择一种模式。

- **初始化**：创建缺失的代码库级目录和基础文件；已有文件保持不变。
- **审计**：只检查结构、必要内容和 Markdown 本地引用，不修改文件。
- **补齐**：先审计，再只创建缺失项；除非用户明确要求，不改写已有内容。

读取目标仓库现有的 `CLAUDE.md`、`REVIEW.md`、`docs/sdlc/`、构建配置、CI 配置和项目说明。先报告工作区中已有的未提交改动，并避免覆盖或整理与本次请求无关的内容。

## 固定边界

- 只创建或检查根目录 `CLAUDE.md`、`REVIEW.md`、`docs/sdlc/00_Index.md`、`docs/sdlc/changes/` 和 `docs/sdlc/incidents/`；空父级目录使用 `.gitkeep` 保持可版本控制。
- 不分配 change ID，不创建 `changes/<change-id>/` 或 `incidents/<incident-id>/`，也不创建 `intent.md`、`spec.md`、`plan.md`、`verification.md`、事故记录或证据文件。
- 不复制 PR、CI、部署或事故系统的完整记录。总索引只保存必要摘要、ID、链接和 commit SHA。
- 不根据通用最佳实践发明团队命令、架构、评审政策、批准角色、Hook、权限或分支保护规则。未知项保留为 `待团队填写`，并说明需要哪个负责人确认。
- 不自动安装或复制其他 Skills。仓库级 Skills 可以通过插件分发，也可以在用户明确选择后放入 `.claude/skills/`。
- 初始化和补齐不得覆盖已有文件。修改已有治理内容必须取得用户明确授权，并保持原有风格和事实来源。

## 初始化与补齐

1. 从 Skill 目录执行：

   ```bash
   python3 scripts/sdlc_scaffold.py init --target <repository>
   ```

2. 只对本次新增文件补充能够从代码库权威文件中验证的信息：
   - `CLAUDE.md` 记录构建、测试和 lint 命令、健康输出、关键约定、架构边界与重复错误。
   - `REVIEW.md` 记录评审轮次、Important 与 Nit 的定义、Nit 上限、忽略项和人工批准边界。
   - `docs/sdlc/00_Index.md` 只维护活动变更、近期完成项和近期事故的入口。
3. 命令优先从项目清单、任务运行器和 CI 配置中确认；不要只根据文件名猜测。无法确认时保留占位说明，不执行可能改变依赖或外部状态的命令。
4. `CLAUDE.md` 应保持精简，只包含新成员开始工作所需的仓库事实。Hook、CI 和权限属于确定性控制；只有团队提供书面规则且用户明确要求时才另行实现。
5. 再运行审计，确认新骨架完整且本地引用有效。

## 审计

运行：

```bash
python3 scripts/sdlc_scaffold.py audit --target <repository>
```

审计结果按以下方式处理：

- `ERROR`：缺少核心文件或目录、本地 Markdown 引用失效、已有阶段产物位于错误位置，或单项变更 / 事故目录缺少入口文件。
- `WARN`：核心文件存在，但缺少文档约定的重要章节或仍含待团队填写的信息。
- `OK`：本次检查范围内没有错误；这不代表产物、政策、PR 或部署已经获得批准。

审计模式只报告发现。用户要求修复时，先列出将新增和将修改的文件；优先创建缺失项，修改已有文件时只处理与发现直接相关的部分。

## 输出

交付时分别列出：

1. **新增文件和目录**。
2. **未修改的已有文件**。
3. **结构检查结果**，包含错误、警告、证据路径和建议负责人。
4. **明确未执行的事项**，至少说明没有创建 change ID、单项变更目录或阶段产物，也没有代替人工设置批准结论。

## 完成检查

- 重复初始化不会改变任何已有文件。
- 根目录治理文件与 `docs/sdlc/` 父级结构齐全，本地引用有效。
- 新增内容只包含可验证的仓库事实；未知项未被猜测补全。
- 没有创建任何单项变更或阶段产物，没有复制外部权威记录。
- 审计发现不被表述为人工批准、政策结论或生产授权。
