# Compose Spec

把已经接受的意图转换为工程团队可以据此制定计划的需求与高层设计规范。输出仍是待评审草稿；产品负责人批准、政策负责人处理政策问题、技术负责人处理高风险事项后，它才成为正式阶段产物。

## 边界

- 以已接受的 `intent.md` 为来源。无法确认接受状态时仍可生成草稿，但必须标明来源状态与风险，不能声称已经进入正式设计阶段。
- 规定需要交付的行为、体验、系统边界和约束，不写文件、类、函数、实施顺序、具体测试代码等 `plan.md` 内容。
- 不把缺失信息补成业务决定、政策例外或架构结论。能够继续时，把缺口写入“未决问题”；缺口会实质改变目标、范围或安全边界时，先请求人工决定。
- 适用的品牌、安全、合规、UX 和 API 规则由对应政策或专项 Skill 提供。缺少权威政策输入时记录缺口，不凭常识冒充组织政策。
- 不执行提交、审批、流程触发或生产操作，除非用户对相应动作另有明确授权。

## 工作模式

根据请求选择一种模式，不同时重写和审核同一文件。

### 生成或补全

1. 完整读取 `intent.md`，确认来源标识、接受状态、目标、约束、范围外内容和未决问题。再读取用户指定的原型、代码库背景与政策输出。
2. 判断哪些领域规则适用。只加载与变更相关的政策 Skills；记录使用的 Skill、政策来源和可得版本。无法取得版本时写 `待确认`。
3. 区分来源事实、已批准决定、政策约束、设计判断和仍待决定的事项。不得让设计判断悄悄扩大意图范围。
4. 使用 [assets/spec.md.tpl](assets/spec.md.tpl) 编写规范。必要章节必须保留；不适用时写明原因，不能静默删除。
5. 为需求、约束与验收条件建立足够的对应关系，使评审者能判断每项重要行为如何验收。复杂规范可使用稳定编号；不要为简单变更制造无意义的编号体系。
6. 交付规范草稿，并单列阻碍批准的问题、政策冲突和需要咨询的负责人。保持状态为 `待评审`，不得代填批准人或批准结论。

### 完整性校验

1. 同时读取现有 `spec.md`、来源 `intent.md` 和规范声明使用的政策材料；缺失输入本身就是发现。
2. 检查必要章节、来源与状态、意图追溯、适用政策、可验证验收条件、风险、未决问题和批准记录。
3. 检查是否混入未经确认的业务决定，是否遗漏意图中的范围外内容或未决问题，是否过早规定实现细节。
4. 按“严重 / 重要 / 建议”输出发现。每项包含证据位置、影响、建议处理方式和需要决定的角色；没有发现时明确说明检查范围与剩余未知项。
5. 校验只给出修订建议，不把自动检查结果写成产品、政策或技术批准。

## 必要内容

`spec.md` 至少应表达以下内容；未知项写 `待确认`，不适用项写 `不适用` 并说明原因。

- 标题、来源、状态、作者或生成者、时间，以及使用的政策或 Skills 记录。
- 目标、范围内与范围外内容，并能追溯到 `intent.md`。
- 受影响用户、关键角色、主要场景、异常场景和权限差异。
- 可观察的功能行为、输入输出、业务规则和失败处理；避免提前固定实现方式。
- 体验与设计要求，包括相关的加载、空、错误、成功和无权限状态；无界面变更时说明不适用原因。
- 系统与集成边界，包括涉及的系统、数据流向、外部依赖和责任边界。
- 可验证的非功能要求，例如性能、可靠性、兼容性、可访问性、可观测性和可维护性；只保留适用项。
- 适用政策的来源、约束、所需证据、例外与责任人；政策正文未知时不得代写。
- 可由后续计划和测试验证的验收条件，并与关键需求或约束对应。
- 风险、政策冲突、影响范围和升级负责人。
- 未决问题、决定人和对批准或计划的影响。
- 产品、政策和技术审核记录的占位信息，不得伪造签字或日期。

## 领域 Skill 路由

生成或审核规范的领域内容时，只加载与变更相关且具有权威输入的 Skills。它们不拥有完整 `spec.md`，也不取代人工批准。

- 客户可见界面、文案或品牌表达使用 `$brand-guidelines`。
- 法律、监管、行业或组织合规约束使用 `$compliance-policy`。
- 身份授权、数据、密钥、依赖、网络、日志或供应链相关约束使用 `$security-policy`。
- 外部 API 的端点专项安全检查交给 `$secure-api-review`；通用安全政策不能替代它。

不要默认运行全部领域 Skills。产品负责人仍需对照 `intent.md` 审核目标、范围和业务决定；高风险与技术可行性问题仍由技术负责人处理。这些人工职责不能被领域 Skill 的输出替代。

## 完成检查

- 所有必要章节存在，不适用项均有理由。
- 重要内容可追溯到意图、明确的设计判断或权威政策来源。
- 未回答的问题没有被伪装成决定，政策冲突没有被静默消解。
- 验收条件描述可观察结果，且覆盖关键需求、非功能要求和政策约束。
- 规范没有滑入实施计划，状态与批准记录没有越过人工关卡。
