# Secure API Review

在规范或契约阶段对外部 API 做针对性的安全检查，把发现转换为可验收的要求。它补充而不取代 `$security-policy` 的通用安全约束，也不代表安全负责人批准。

## 所需输入

- 涉及的接口说明：`spec.md` API 章节、OpenAPI 契约或接口清单。
- 调用方类型（公网用户、合作方、内部服务）、认证方式和数据分类。
- 适用的组织安全政策（通常来自 `$security-policy` 的输出）与已知例外。

缺少数据分类或调用方信息时，相关判断标为 `待确认`，不得假设接口只在内网使用。

## 检查清单

- **认证**：每个端点是否声明认证要求；匿名端点是否有明确理由。
- **授权**：是否有对象级与功能级授权要求；按 ID 访问资源时是否校验归属，避免越权读取或修改。
- **输入校验**：参数与请求体是否有类型、长度、格式、枚举和上限约束；是否拒绝未知字段或说明处理方式。
- **批量与资源消耗**：分页上限、请求体大小、速率限制和超时是否定义。
- **数据暴露**：响应是否只返回必要字段；PII 与敏感字段是否标注、脱敏或按权限返回。
- **错误处理**：错误响应是否避免泄露堆栈、内部标识或存在性信息。
- **审计**：敏感读写、权限变更和失败认证是否记录审计事件，且日志本身不记录秘密或完整 PII。

## 工作流程

1. 若有 OpenAPI 文件，先运行确定性预检：

   ```bash
   python3 scripts/check_openapi.py path/to/openapi.yaml
   ```

   脚本检查缺失安全声明、缺少 401/403 响应、无上限的数组与字符串、疑似 PII 字段。结果只作为线索，需人工复核。
2. 按检查清单逐个端点审查规范与契约，结合调用方和数据分类判断风险。
3. 按“严重 / 重要 / 建议”输出问题：可导致未授权访问或批量数据泄露为严重；缺少校验、限流或审计为重要。
4. 为每个问题给出可写入 `spec.md` 的安全要求和验收条件，不指定具体库或实现。
5. 列出需要安全负责人决定的例外和残余风险。

## 输出格式

1. **范围与输入**：检查的端点、调用方、数据分类、使用的政策和脚本结果。
2. **问题清单**：严重程度、端点、证据、影响、建议要求。
3. **安全要求与验收条件**：可直接引用到规范中的条目。
4. **待决定事项与残余风险**：负责人和对上线的影响。

## 完成检查

- 每个端点都检查了认证、授权、输入校验、数据暴露和审计。
- 脚本结果经过人工复核，没有把预检通过写成“安全”。
- 没有修改代码、没有执行主动攻击测试、没有替安全负责人批准。
