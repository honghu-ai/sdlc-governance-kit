本文按规划、设计、构建、测试、部署和维护六步说明 Skills 的职责。原文只有 `secure-api-review` 使用了明确名称，其余名称均为根据文章中的模板、政策和组织知识类别整理出的建议命名。`compose-spec` 与 `security-policy` 是核对流程后补充的建议 Skill。

## 1. 先区分 Skill 输出与阶段产物

Skill 输出是一次调用产生的结构、约束、检查项或评审发现。阶段产物是经过人工关卡后提交到版本控制，并交给下一阶段读取的正式记录。

`capture-intent` 和 `compose-spec` 负责完整阶段产物。品牌、合规、UX 和安全 Skills 只提供各自领域的内容，不能独立生成整份 `spec.md`。设计阶段的会话、组织级斜杠命令或自动任务负责加载 `compose-spec` 与适用的政策 Skills。

| 概念 | 例子 | 负责人 |
| --- | --- | --- |
| Skill 输出 | 结构化规范、品牌约束、合规问题、UX 验收条件或 API 安全发现 | 对应负责人维护规则，Claude 负责应用 |
| 阶段产物 | `intent.md`、`spec.md`、`plan.md`、代码差异与测试、PR、事故记录 | 每个阶段指定的人工角色批准 |
| 流程编排 | 汇总多个 Skill 输出并生成完整产物 | 会话提示词、斜杠命令、自动任务或 CI |
| 确定性约束 | 阻止危险操作或不合格变更 | Hook、权限、沙箱、分支保护和 CI |

### 1.1 新项目可以直接从意图开始

这些 Skills 同时适用于存量项目和新项目。`capture-intent` 没有前置条件。新项目不需要先准备 `CLAUDE.md` 或决定技术栈，就可以把项目想法整理为 `intent.md`。意图只记录要解决的问题、期望结果、受影响对象、已知约束、范围外内容和未决问题。

产品负责人接受意图后，`compose-spec` 可以在没有现成代码库的情况下生成 `spec.md`。此时，代码库背景可以为空，规范仍应写清用户场景、系统边界、非功能要求、政策约束和验收条件。尚未决定的语言、框架、数据库和部署平台留在未决问题中。只有已经批准并会限制后续方案的技术决定，才作为约束写入规范。

新项目可以按下面的顺序进入产物循环。

```text
项目想法
  ↓
capture-intent
  ↓
intent.md 草稿
  ↓ 发起人修正，产品负责人接受
compose-spec
  ↓
spec.md 草稿
  ↓ 产品审核，按需进行政策与技术审核
计划模式
  ↓
确定必要的技术选型并生成 plan.md
  ↓ 工程师批准
初始化代码库并建立 CLAUDE.md
  ↓
开始实现
```

| 阶段 | 新项目的主要工作 | 技术栈状态 |
| --- | --- | --- |
| `intent.md` | 说明问题、期望结果和边界 | 不需要技术栈 |
| `spec.md` | 规定系统行为、高层边界、适用政策和验收条件 | 只记录已经确认的技术约束，具体选型可以待定 |
| 规范审核 | 产品负责人检查意图一致性，政策负责人处理适用规则，技术负责人处理高风险和可行性问题 | 找出进入计划前必须决定的技术问题 |
| `plan.md` | 明确实施路径、文件范围、工作顺序和验证方法 | 确定足以支持实施的技术选型 |
| 代码库初始化 | 创建项目结构、命令和反馈循环 | 将已经采用的技术栈、架构和约定写入 `CLAUDE.md` |

`CLAUDE.md` 保存代码库当前采用的技术栈、命令、架构和常见错误。它在技术选择逐渐形成后建立，不负责在意图阶段替团队选择技术。新项目没有现成品牌、安全、合规或 UX 政策材料时，应在 `spec.md` 中记录缺口和责任人，不能用通用建议冒充组织政策。

## 2. 六步流程总览

| 步骤  | 正式产物                     | 主要 Skills                                                 | 是否缺少 Skill | 判断                                                      |
| --- | ------------------------ | --------------------------------------------------------- | ---------- | ------------------------------------------------------- |
| 规划  | `intent.md`              | `capture-intent`                                          | 否          | 已能把想法、工单或事故发现整理成统一意图                                    |
| 设计  | `spec.md`                | `compose-spec`，并按任务加载品牌、合规、UX、安全和 API Skills              | 否          | `compose-spec` 保证结构完整，政策 Skills 提供领域约束                  |
| 构建  | `plan.md`，随后产生代码变更       | API 任务使用 `api-design-conventions` 和 `secure-api-review`   | 否          | `plan.md` 由计划模式生成，其他实现遵循已批准的 `spec.md`                  |
| 测试  | 代码差异、测试与验证证据             | API 任务使用 `api-design-conventions` 和 `secure-api-review`   | 否          | 通用验证直接执行 `spec.md` 的验收条件，并由测试命令、反馈循环和 CI 完成             |
| 部署  | PR、评审发现与批准记录             | API 专项评审使用 `api-design-conventions` 和 `secure-api-review` | 否          | `REVIEW.md` 负责对照 `spec.md`、`plan.md` 和代码差异，发布关卡由确定性机制执行 |
| 维护  | 事故记录，必要时生成新的 `intent.md` | 复用 `capture-intent`                                       | 否          | 监控与分级响应属于确定性脚本、控制带配置和操作手册                               |

## 3. 第一步　规划

### 3.1 使用 `capture-intent`

| 项目 | 定义 |
| --- | --- |
| 输入 | 发起人的想法、业务问题、缺陷工单、事故发现或改进建议 |
| Skill 输出 | 结构化意图草稿、需要澄清的问题和未决事项 |
| 阶段产物 | 经发起人纠正并由产品负责人接受的 `intent.md` |
| 作用 | 保留问题来源和原始意图，让设计阶段可以直接读取 |
| 主要内容 | 问题、期望结果、受影响用户与系统、约束、范围外内容和未决问题 |

`capture-intent` 是两个产物生成 Skills 之一。它负责把原始材料整理为 `intent.md`，不能替发起人补充未经确认的业务决定。

使用示例

```text
请使用 capture-intent Skill 整理这次讨论，生成 intent.md。保留问题的原始描述，列出约束和未决问题，不要自行补全业务决定。
```

### 3.2 是否需要新增 Skill

当前不需要。意图可能来自人员讨论、工单和生产事故，但它们都可以进入同一个 `capture-intent`。来源连接器、提交动作和审批流程属于流程编排，不需要分别写成 Skill。

## 4. 第二步　设计

### 4.1 使用 `compose-spec` 生成完整 `spec.md`

设计阶段的流程读取已经接受的 `intent.md`，加载 `compose-spec` 和适用的政策 Skills，再汇总成完整的 `spec.md`。

| 项目 | 定义 |
| --- | --- |
| Skill 输入 | 已接受的 `intent.md`、必要的设计原型、代码库背景和政策 Skills 输出 |
| Skill 输出 | 结构完整的规范草稿、缺失信息和需要人工处理的问题 |
| 阶段产物 | 经产品负责人批准的 `spec.md` |
| 作用 | 规定系统需要交付的行为和必须满足的约束，供工程师制定计划 |
| 主要内容 | 来源、目标、范围、用户场景、功能需求、体验设计、系统边界、非功能要求、政策约束、验收条件、风险、未决问题和批准记录 |

`compose-spec` 同时支持生成和校验。生成时根据 `intent.md` 创建完整规范，校验时检查现有文件是否缺少必要章节、验收条件、来源关系或批准记录。某个章节不适用时，应在文件中记录不适用的原因，不能直接省略。

`spec.md` 至少包含以下结构。

```markdown
# Spec　变更名称

来源为 intent.md
状态为待评审

## 目标与范围

## 用户与使用场景

## 功能需求

## 体验与设计要求

## 系统与集成边界

## 非功能要求

## 政策约束

## 验收条件

## 风险与政策冲突

## 未决问题

## 批准记录
```

使用示例

```text
请使用 compose-spec Skill 读取已经批准的 intent.md，加载适用的政策 Skills，并生成完整的 spec.md。缺少的信息列入未决问题，不要自行补充业务决定。所有必要章节必须保留，不适用的章节写明原因。
```

流程入口可以命名为 `/compose-spec`。斜杠命令负责启动和编排，`compose-spec` 负责规范结构与完整性，政策 Skills 负责各自领域的约束。

### 4.2 `brand-guidelines`

| 项目 | 定义 |
| --- | --- |
| 触发条件 | 变更包含客户可见界面、文案或品牌表达 |
| Skill 输出 | 适用的品牌约束、品牌验收条件、违规项和冲突项 |
| 产物关系 | 输出写入或用于评审 `spec.md` 的品牌相关内容，不拥有完整 `spec.md` |
| 作用 | 让品牌政策在规范形成和规范评审时得到应用 |
| 主要内容 | 视觉规则、语气与术语、禁止用法、品牌例外和升级负责人 |

使用示例

```text
我们正在编写 spec.md。请使用 brand-guidelines Skill，只输出适用的品牌约束、验收条件和需要品牌负责人判断的问题，不要改写其他需求。
```

### 4.3 `compliance-policy`

| 项目 | 定义 |
| --- | --- |
| 触发条件 | 变更受到法律、监管、行业或组织合规政策约束 |
| Skill 输出 | 合规义务、证据要求、政策冲突和需要人工裁决的问题 |
| 产物关系 | 输出写入或用于评审 `spec.md` 的合规部分，不拥有完整 `spec.md` |
| 作用 | 在工程团队制定计划前识别合规要求和不可自动决定的事项 |
| 主要内容 | 政策来源、适用范围、数据保留、审计证据、批准角色和例外流程 |

使用示例

```text
我们正在编写 spec.md。请使用 compliance-policy Skill，只补充适用的合规约束、验收证据和需要人工裁决的问题，不要改写其他需求。
```

### 4.4 `ux-standards`

| 项目 | 定义 |
| --- | --- |
| 触发条件 | 变更影响用户流程、界面状态、交互或可访问性 |
| Skill 输出 | UX 要求、界面状态、可访问性检查项和体验验收条件 |
| 产物关系 | 输出写入或用于评审 `spec.md` 的 UX 部分，不拥有完整 `spec.md` |
| 作用 | 把用户体验标准转成工程团队可以实现和验证的条件 |
| 主要内容 | 主流程与异常流程、加载和空状态、错误反馈、可访问性和视觉验证目标 |

使用示例

```text
我们正在编写前端 spec.md。请使用 ux-standards Skill，只输出用户流程、界面状态、可访问性要求和验收条件，不要决定技术实现。
```

### 4.5 API 任务使用的 Skills

| Skill | Skill 输出 | 产物关系 | 作用 | 主要内容 |
| --- | --- | --- | --- | --- |
| `api-design-conventions` | API 契约约束和设计检查结果 | 写入或评审 `spec.md` 的 API 边界 | 统一接口设计 | 路径与字段命名、版本、Schema、分页、错误格式和兼容性 |
| `secure-api-review` | API 安全要求、问题列表和端点检查结果 | 写入或评审 `spec.md` 中的 API 安全要求，后续继续验证实现 | 限制外部端点风险 | 身份认证、输入校验、审计事件、PII 和检查脚本输出 |

这两个 Skills 只在任务涉及 API 时加载，不能替代通用安全政策。

### 4.6 缺少的 `security-policy`

设计阶段需要安全政策 Skill。当前 `secure-api-review` 只覆盖外部 API，无法处理文件上传、后台任务、消息队列、权限模型、依赖、网络访问和密钥等非 API 场景，因此建议增加 `security-policy`。

| 项目 | 建议定义 |
| --- | --- |
| 输入 | `intent.md`、系统边界、数据类型和组织安全政策 |
| Skill 输出 | 安全约束、威胁关注点、验收条件和需要安全负责人判断的问题 |
| 产物关系 | 输出写入或用于评审 `spec.md` 的安全部分，不拥有完整 `spec.md` |
| 作用 | 为所有软件变更提供通用安全约束，API 专项检查仍交给 `secure-api-review` |
| 主要内容 | 身份与授权、数据分类、密钥、依赖、网络边界、日志、供应链和升级条件 |

建议使用示例

```text
我们正在编写 spec.md。请使用 security-policy Skill，只输出适用的安全约束、验收条件和需要安全负责人判断的问题。API 专项要求交给 secure-api-review。
```

## 5. 第三步　构建

### 5.1 计划模式负责生成 `plan.md`

| 项目 | 定义 |
| --- | --- |
| 流程输入 | 已批准的 `intent.md`、`spec.md`、代码库和 `CLAUDE.md` |
| 流程输出 | 可供另一名工程师直接执行的实施计划 |
| 阶段产物 | 经工程师批准的 `plan.md`，高风险计划由技术负责人或架构师批准 |
| 作用 | 在代码生成前明确实施路径和验证方法 |
| 主要内容 | 修改文件、工作顺序、风险、被放弃的方案和用于证明正确的测试 |

这里不需要通用的 `build` 或 `write-plan` Skill。Claude Code 计划模式负责读取代码库并生成计划，代码库命令、架构和常见错误放在 `CLAUDE.md` 中。

### 5.2 只使用明确支持代码的 Skills

| Skill | 构建阶段输出 | 与产物的关系 | 作用 | 主要内容 |
| --- | --- | --- | --- | --- |
| `api-design-conventions` | API 实现检查项和偏差说明 | 影响 `plan.md` 和代码差异 | 保证实现遵守已经批准的 API 契约 | 命名、版本、Schema、错误格式和兼容性 |
| `secure-api-review` | API 安全检查结果与脚本输出 | 附在会话记录和后续 PR 检查中 | 在端点实现时发现安全问题 | 认证、输入校验、审计和 PII |

`brand-guidelines`、`compliance-policy`、`ux-standards` 和 `security-policy` 负责设计阶段的规范内容。构建阶段直接遵循已经批准的 `spec.md`，不重新加载这些 Skills。只有明确写有代码级规则和检查方法的 Skill 才能检查实现。

### 5.3 是否需要新增 Skill

当前不需要通用构建 Skill。必须无条件执行的要求交给 Hook，例如保护冻结目录、阻止凭据写入和运行格式检查。Skill 负责提示和检查，Hook 负责阻止违规动作。

## 6. 第四步　测试

### 6.1 直接执行 `spec.md` 的验收条件

| Skill | 测试阶段输出 | 阶段产物 | 作用 | 主要内容 |
| --- | --- | --- | --- | --- |
| `secure-api-review` | 端点检查脚本结果和安全问题 | 代码差异、测试及安全检查证据 | 验证 API 安全要求 | 认证、输入校验、审计和 PII |
| `api-design-conventions` | Schema 或契约检查结果 | 代码差异、契约测试和 lint 结果 | 验证 API 兼容性 | 版本、字段、错误格式和兼容性 |

测试阶段通常不需要重新调用设计阶段的政策 Skills。品牌、UX、合规和通用安全要求已经写入获批的 `spec.md`，测试通过确定性命令、截图比较和验收记录证明这些条件是否成立。若以后需要模型检查代码或视觉结果，应另建明确支持实现验证的专项 Skill。

### 6.2 是否需要新增 Skill

当前不需要通用测试 Skill。测试命令、健康输出和完成标准写入 `CLAUDE.md`，反馈循环负责反复运行，最终验证可以交给独立子智能体，CI 和 Hook 负责确定性执行。只有当组织存在跨代码库且需要统一解释的验证证据政策时，才值得另建政策 Skill。

## 7. 第五步　部署

### 7.1 PR 评审以 `spec.md` 和 `plan.md` 为准

| 评审范围 | 使用的 Skills | Skill 输出 | 阶段产物 | 作用 | 主要内容 |
| --- | --- | --- | --- | --- | --- |
| API 安全 | `secure-api-review` | 按严重程度排列的 API 安全发现 | PR 与安全评审记录 | 识别端点实现中的安全问题 | 认证、输入校验、审计和 PII |
| API 设计 | `api-design-conventions` | 契约和兼容性问题 | PR 与 API 评审记录 | 防止破坏接口约定 | 命名、版本、Schema、错误格式和兼容性 |

完整 PR 评审还需要检查缺陷、逻辑错误以及代码是否符合 `spec.md` 和 `plan.md`。品牌、UX、合规和通用安全要求通过获批的 `spec.md` 进入评审，不重新加载设计阶段 Skills。评审轮次、严重程度和忽略项写入 `REVIEW.md`。

### 7.2 是否需要新增 Skill

当前不需要通用 `pr-review` 或 `deploy` Skill。`REVIEW.md` 负责评审编排，Claude 集成或 CI 负责执行，分支保护和代码负责人负责最终批准，生产授权由 Hook 和 CI/CD 关卡执行。

## 8. 第六步　维护

### 8.1 复用 `capture-intent` 将发现送回流程

| 项目 | 定义 |
| --- | --- |
| 输入 | 控制带越界、缺陷工单、频道消息、安全发现或定期扫描结果 |
| Skill 输出 | 包含异常证据、期望结果、受影响系统和未决问题的意图草稿 |
| 阶段产物 | 事故记录，以及经服务负责人分流后提交的新 `intent.md` |
| 作用 | 将生产发现转换成第一阶段可以直接接手的格式 |
| 主要内容 | 触发时间、异常证据、影响范围、已经执行的动作、期望结果和未决问题 |

使用示例

```text
请使用 capture-intent Skill 将这次控制带越界的诊断整理成 intent.md。保留指标、时间戳和受影响系统，列出已经执行的动作与未决问题，不要自行决定修复优先级。
```

### 8.2 是否需要新增 Skill

当前不需要通用维护 Skill。监控必须由确定性脚本完成，响应等级写入受版本控制的控制带配置，允许执行的动作写入操作手册，诊断由受权限限制的智能体任务完成。

如果多个服务已经形成统一且需要人工解释的事故分流政策，可以再评估 `incident-triage-policy`。它应只输出严重程度建议、责任人和升级路径，不能负责检测异常、直接操作生产环境或批准修复。

## 10. Skills 的边界

| 内容 | 合适载体 |
| --- | --- |
| 单个代码库的命令、架构和常见错误 | `CLAUDE.md` |
| 一次性任务要求 | 当前提示词 |
| 固定工作流入口、触发和多 Skill 编排 | 组织级斜杠命令或自动任务 |
| 完整产物的固定结构与必要内容 | 产物生成 Skill |
| 必须无条件执行的限制 | Hook、权限、沙箱、分支保护或 CI |
| PR 评审轮次、严重程度和忽略项 | `REVIEW.md` |
| 重复的最终验证、研究或简化工作 | 子智能体 |
| 生产监控和响应等级 | 确定性脚本、控制带配置和操作手册 |

新增 Skill 前应确认三件事。

1. 这项知识需要在多个任务中一致应用。
2. 它有明确的政策负责人和书面唯一事实来源。
3. 它不属于 `CLAUDE.md`、一次性提示词、工作流命令或必须确定执行的控制机制。
