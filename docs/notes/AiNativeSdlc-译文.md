## 1. 代码已不再是瓶颈

各组织已经开始用 AI 编写代码，速度快到一年前还难以想象，围绕代码的流程却没有同步变化。

许多工程团队仍然保留原有的审批关卡、评审、交接流程和政策。这些环节拖慢了 Claude Code 等智能体编程方案带来的生产力提升。

软件开发生命周期，也就是 SDLC，指软件从想法进入生产环境的完整过程。多数组织采用的流程都包含六个阶段，即规划、设计、构建、测试、部署和维护。传统上，每个阶段都是独立环节，由不同角色负责。产品经理编写需求，技术架构师将需求转成设计，工程师根据设计实现功能，受监管企业中的 QA 团队负责验证，发布团队负责上线，运维团队监控生产系统。工作依靠文档、工单和签字确认在各阶段之间流转。

传统 SDLC 包含大量流程，目的是在每一步确保责任清晰并维持控制。它形成于编写和实现代码最耗时、成本最高的年代，因此围绕这一条件追求效率。产品需求文档、估算仪式和产品安全评审，都用于迫使团队在可能持续数周、数月甚至数个季度的开发工作中保持一致。

传统 SDLC 的控制措施还假定每一步都由人完成。获得最多价值的组织已经围绕智能体 AI 当前能完成的工作重建流程，同时确保人类仍然参与其中。本文结合 Anthropic 与客户合作的经验，介绍其 Applied AI 团队在 SDLC 各阶段内部集成 Claude 的实践，用于加快开发并提高流程效率。

当代码不再是瓶颈，构建阶段的速度超过传统 SDLC 所允许的节奏时，会出现三个变化。

1. 瓶颈转移到构建阶段的前后两侧，主要落在规划、评审与测试、部署等仍以人类速度运行的环节。
2. 原有控制措施逐渐无法对应实际情况，也难以执行。代码由人编写时，逐行人工评审有其合理性；当大部分差异由智能体生成后，这种做法无法跟上产出速度。
3. 治理成本上升，因为例外情况仍要交给每周或每月才召开一次的会议与委员会处理。

![](../50_Assets/AI-NativeSdlc/02-BuildBottleneck.png)

<center>构建已不再是制约因素，周围以人类速度运行的步骤才是。当构建时间缩短到数小时，其他阶段的耗时仍维持原状。</center>

以安全瓶颈为例。安全团队的规模通常按照人类编写代码的产出量配置。当智能体让代码产出成倍增加时，安全评审队列会不断积压，或者代码会在评审不足的情况下上线。受监管组织无法接受其中任何一种结果，因此安全与政策检查必须跟上智能体的速度。

要充分发挥智能体 AI 的生产力并保障其安全，传统 SDLC 需要经历与实现阶段同等程度的改造。

## 2. 什么是 AI 原生 SDLC

AI 原生 SDLC 重新设计了软件交付流程，将旧有的控制目标与新的执行方式结合起来。流程从线性流转变成循环，AI 嵌入每一个节点。它推动自动交接并自动触发后续动作，改善传统 SDLC 各阶段之间依靠人工完成的笨重交接。

这种转变也被称作智能体 SDLC、AI SDLC 或智能体软件开发。这些名称不同，指向的是同一件事。

![](../50_Assets/AI-NativeSdlc/03-SixStages.png)

### 2.1 AI 原生 SDLC 六个阶段的变化

下表展示传统 SDLC 与 Claude 支持的 AI 原生 SDLC 两端的状态。大多数组织目前位于两者之间。

| 阶段 | 传统 SDLC | AI 原生 SDLC |
| --- | --- | --- |
| 规划 | 委员会收集需求，通过研讨会和签字流程逐步提炼，再由人手工编写 | Claude 直接从信息源汇总痛点，写入人类可读且机器可执行的 `intent.md` |
| 设计 | 分析师编写规范，设计师再解析规范 | 需求和设计压缩到一次与智能体协作的会话中，由编码成 Skills 的标准约束，并在 git 中进行版本管理 |
| 构建 | 测试和代码由人手写，文档通常在主要开发完成后补写 | 测试和代码由 AI 生成，组织知识以机器可读且经过版本管理的 `CLAUDE.md` 与 Skills 保存 |
| 测试 | 在阶段边界设置 QA 关卡 | 持续评估贯穿实现过程 |
| 部署 | 人工评审每一行代码，治理按评审周期执行，实际执行往往不一致 | 多层智能体评审承担常规检查，人工评审留给受监管代码和关键代码。治理在 AI 执行动作时完成，Hooks 充当审批关卡 |
| 维护 | 人工监控生产环境中的缺陷 | 智能体监控线上部署。任何超出控制带的异常都会得到诊断，并作为新的 `intent.md` 写回循环 |

右侧各阶段有一条共同主线，即已经提交的产物。每个阶段结束时都会向版本控制系统写入一个产物，包括 `intent.md`、`spec.md`、`plan.md`、代码差异及测试、包含评审结果的 PR，以及事故记录。下一个阶段从读取它开始。

在早期阶段，主要产物是 Markdown 文件，因为产品负责人和智能体都能阅读同一份文件并据此行动。从构建阶段开始，产物转为代码及其相关记录。

提交链同时构成审计记录，说明谁提出了什么要求、智能体生成了什么，以及谁批准了结果。凡是需要判断的决策，最终责任仍由人承担。在智能体 SDLC 中，人的注意力会随着待评审产物的位置而移动。

每个阶段都会提交一个可供下一个阶段读取的产物。意图、规范、计划、代码差异和评审结果共同组成审计记录。

## 3. 实战方案

本手册的核心方案分布在规划、设计、构建、测试、部署和维护六个非线性阶段，合起来覆盖完整生命周期。

每项方案都包含以下内容。

1. 发生了什么变化
2. 如何开始
3. 具体实施步骤
4. 治理事项
5. 如何衡量实施效果

这些步骤彼此独立。组织可以根据自身需要，在不同时期优先改造不同阶段。每项方案都会在前置条件中列出依赖关系，依赖图也会进一步展示这些关系。

一个阶段通过提交产物结束，这次提交会启动下一个阶段。被接受的 `intent.md` 触发需求和设计流程，获批的 `spec.md` 触发计划模式，合并后的 PR 触发流水线，生产环境中的控制带越界则写出下一份 `intent.md`，循环由此持续运行。

最初可以由人手动提示每一步。最终状态是每个被接受的产物自动触发下一道关卡。人的注意力集中在这些关卡上，评审智能体标记的问题，不必从头启动每个阶段。

![](../50_Assets/AI-NativeSdlc/04-AdoptionOrder.png)

<center>图中列出了各项方案所属的阶段，箭头表示采用顺序，两者并不相同。没有箭头指向的浅棕色方案没有前置依赖，可以优先开始。其他方案应先完成箭头指向它的依赖项。</center>

## 4. 第一阶段 规划

想法不必继续等待别人把它写成正式材料。发起人只需用自己的语言记录一次意图，形成有版本记录、可供下一阶段直接使用的产物。

### 4.1 将想法记录为 `intent.md`

启动软件开发流程的 `intent.md` 可以从不同入口产生。有人提出想法，可以形成一张工单，也可以由告警暴露一项事故，后者会在第六阶段说明。

当一个人产生想法时，可以与 Claude 进行头脑风暴，得到一份 Markdown 格式的初步规范。在传统 SDLC 中，同一个人还要说服产品团队成员与自己一起编写，或者请对方代写。

Claude 生成的初步规范既能供人阅读，也能进行版本管理，并且可以立即交给下一阶段使用。这个文件保存为 `intent.md`。

无论意图来自事件触发器还是智能体，后续步骤都相同。产品负责人在提交之前评审并修正由智能体编写的 `intent.md`。

传统流程中，一个想法要经过待办项、用户故事、故事点和需求梳理会议才能进入执行。每次交接都会转移所有权，工程团队最终收到的内容已经与发起人的原意隔了好几层。

AI 原生流程中，发起人与 Claude 进行头脑风暴，再将结果写成 `intent.md`。这是一份用发起人自己的语言编写的初步规范，其中说明想要什么、原因和约束。重复流程则编码成 Skills。

#### 前置条件

无。

#### 基础设施

为非工程人员提供 Claude 访问权限，可使用 claude.ai 或 Cowork；准备一份约定好的 `intent.md` 模板；建立一个共享、受版本控制且由产品负责人关注的意图存放位置。

对于单个产品，最简单的做法是在产品代码库中建立 `intent/` 目录，让产物链靠近最终产生的代码。只有当意图横跨多个代码库时，独立的意图仓库才值得承担额外成本。在单一代码仓库中，它只是一个目录。

第三阶段关于构建的侧栏会说明，这个存放位置如何与已经保存正式记录的 Jira 或需求工具配合。

这项基础设施只需由平台或工程团队设置一次。技术团队成员需要建立意图存放位置并决定谁有写入权限，因为贡献者可能来自组织内的多个部门。

仓库建立后，不熟悉 git 的贡献者无需直接操作 git。连接 GitHub 等版本控制系统后，Claude 可以代他们从 claude.ai 或 Cowork 提交 Markdown 文件。

#### 实施步骤

1. 发起人用自己的语言向 Claude 描述问题，可以说明当前做不到什么、想法影响哪些人、期望的改善结果，或者哪些内容不在范围内。无需使用正式术语。
2. 持续讨论，直到想法足够具体。Claude 会询问分析师通常关注的问题，包括范围、用户、约束和成功标准。
3. 要求 Claude 使用组织模板把结果写成 `intent.md`。模板可以编码为 Skill，由技术团队成员建立并交由负责人批准。模板可以覆盖问题、期望结果、受影响的用户和系统、约束及未决问题。
4. 发起人修正 Claude 理解错误的内容。
5. 将 `intent.md` 提交到共享位置。作者和时间戳随之进入记录，产品负责人从这里接手想法。

#### 示例

```markdown
# 意图　理赔状态自助查询

作者：J. Ortiz（理赔运营）
状态：草稿

## 问题

客户会致电联络中心询问理赔进度。
理赔处理人员约三分之一的通话时间用于回答只涉及状态的问题。

## 期望结果

客户可以在门户中查看理赔状态、下一步操作和预计日期。

## 受影响的用户与系统

理赔处理人员、门户团队、claims-core API。

## 约束

门户会话中不得增加新的个人身份信息。只能使用现有身份认证。

## 未决问题

第三方损失理算员是否也需要访问权限？
```

#### 治理事项

证据是已经提交的 `intent.md`，其中包含作者、时间戳和完整修订历史。这些信息记录在意图存放位置的 git 历史中。产品负责人负责批准，决定意图进入第二阶段还是被拒绝。这个决定记录为合并或关闭评审。

#### 衡量方式

领先指标是从第一次对话到提交 `intent.md` 所用的时间，可以从意图仓库的 git 历史中读取作者和时间戳。期望结果是把持续数周的需求发掘和细化周期缩短到数小时。

滞后指标包括 `intent.md` 的存活率，即被产品负责人接受并进入第二阶段的比例，而非被关闭的比例。接受或拒绝记录为产物合并或评审关闭。另一个指标是同一项变更首次提交 `spec.md` 后，`intent.md` 又发生了多少次修改。

## 5. 第二阶段 设计

需求和设计被压缩到一次会话中。政策在规范编写时就得到应用，不必等到数周后的评审才发现问题。

### 5.1 需求与设计

产品负责人批准意图后，Claude 会读取已经接受的 `intent.md`，生成需求与设计规范。组织围绕品牌、安全、合规和用户体验编写的 Skills 会指导这一过程。

产品负责人负责评审规范，但不亲自编写。目标是形成一份工程团队可以据此制定计划的规范，并标出需要关注的问题。

前端工作最能说明这一过程。`intent.md` 被接受后，产品负责人根据它在 Claude Design 测试版中制作设计原型，持续调整，再导出到 Claude Code 中实现。

传统流程把需求和设计分配给不同团队。分析师将想法写成正式需求，设计师再把需求解析成设计。这样的分工有助于划分责任，但速度较慢，也容易损失信息。

AI 原生流程在一次提示会话中完成两个阶段。Claude 读取 `intent.md`，在组织 Skills 的约束下生成需求与设计规范，同时标出关注点。

#### 前置条件

一份 `intent.md`，以及已经编写成 Skills 的品牌、安全、合规和用户体验政策。

#### 基础设施

一名拥有 Claude 访问权限的产品负责人，不要求具备工程技能。

#### 实施步骤

1. 产品负责人开启一个可以使用组织 Skills 的会话，并附上 `intent.md`。
2. 提示词指向 `intent.md`，列出约束并要求标记关注点。最初可以手动运行，之后将流程固化成组织级斜杠命令。再往后，可以把意图存放位置中 `intent.md` 的接受动作设为触发器，在合并时启动非交互任务，加载组织 Skills 执行流程，并以拉取请求形式提交 `spec.md`。第五阶段的 CI/CD 方案会说明底层流水线。完成自动化后，产品负责人的首次介入点就是评审。
3. 同一名产品负责人对照原始想法评审规范。规范是否解决了已经描述的问题，`intent.md` 中的未决问题是否已经得到回答或被带到下一步。
4. 优先处理已标记的关注点，因为分析师也会将这些问题升级。产品负责人应在工程团队看到规范前，与对应的政策负责人解决每个问题。
5. 将 `spec.md` 与 `intent.md` 一起提交。这组文件记录提出了什么要求，以及最终做了什么决定。
6. 产品负责人决定规范和意图是否进入构建阶段。凡被组织归为高风险的事项都应咨询技术负责人。这个决定始终由人作出，接受规范后才会启动第三阶段的计划模式。

#### 提示词示例

```text
阅读随附的 intent.md，并为它编写一份集成到现有代码库中的需求与设计规范。使用当前可用的 Skills，确保方案符合我们的品牌指南、安全政策和用户体验标准。将完整规范记录到 spec.md，使其可以直接交给工程团队。清楚说明所有需要关注的问题，尤其是无法同时满足相互冲突政策的情况。
```

#### 治理事项

当前生效的政策会在规范编写时被读取并应用。组织 Skills 充当规范的约束。规范、生成规范的提示词，以及当时生效的 Skill 版本都会记录到版本控制系统。产品负责人签字确认规范，并把已标记的问题交给对应的政策负责人。

#### 衡量方式

领先指标是同一项变更的 `intent.md` 提交和 `spec.md` 提交之间的时间，可由两个 git 时间戳计算，并与过去的需求加设计周期比较。

滞后指标是构建开始后的需求返工量。统计同一项变更首次提交 `plan.md` 后发生的所有 `spec.md` 提交，git log 可以直接提供数据。

## 6. 第三阶段 构建

未经接受的计划，不进入实现。组织知识转成智能体会读取的文件，约束也以代码形式执行，不再依赖个人习惯。

### 6.1 默认从 Claude Code 计划模式开始

工程师在 Claude Code 中以计划模式开启会话，提供第二阶段批准的 `spec.md`。Claude 会向工程师提问，双方持续调整计划，直到工程师满意。

传统流程中，工程师读完设计就开始写代码。具体会修改哪些文件、如何修改以及怎样测试，通常只存在于工程师脑中，最多写在工单评论里。其他人无法提前评审，评审者第一次看到的是已经完成的代码差异，此时返工成本已经较高。

AI 原生流程先由 Claude 在计划模式下阅读代码库并形成书面计划，此时它不能修改文件。工程师在代码生成之前修正计划，再把批准版本提交为 `plan.md`，供后续阶段核对。

#### 前置条件

如果已有意图产物，应提供 `intent.md` 或 `spec.md`。拥有 `CLAUDE.md` 会让流程更顺畅。

#### 基础设施

能够访问代码库的 Claude Code。

#### 实施步骤

1. 工程师以计划模式开启 Claude 会话。
2. 提供 `intent.md` 和 `spec.md`，要求 Claude 制定实现计划，列出将修改的文件、工作顺序和用于证明实现正确的测试。
3. 追问计划可能破坏什么、哪一步风险最高，以及 Claude 放弃了哪些替代方案。
4. 持续调整，直到一名没有看过会话记录的工程师也能仅凭计划完成实现。
5. 将批准后的计划提交为 `plan.md`。它会进入审计记录，第五阶段的 PR 评审将据此核对最终代码差异。
6. 接受计划并让 Claude 实现。计划足够扎实时，实现通常可以一次完成。
7. 实现偏离计划时，在同一次提交中更新 `plan.md`。可以考虑使用 Hook 强制两者同步。

#### plan.md 示例

```markdown
# 计划　理赔状态自助查询

来源为 2026-06-02 的 intent.md

## 修改的文件

portal/src/claims/StatusPanel.tsx（新增）
claims-api/routes/status.py
claims-api/tests/test_status.py

## 工作顺序

1. 在现有身份认证之后增加状态端点。
2. 让面板调用该端点。
3. 将面板接入门户导航。

## 风险

claims-core API 的速率限制为每秒 50 次请求，面板必须使用缓存。

## 证明

test_status.py 覆盖四种理赔状态，截图与批准的原型一致。
```

#### 治理事项

设计评审发生在代码生成之前。此时改变方向只需编辑文档。计划模式本身也会执行这项约束，因为工程师接受计划前，Claude 无法编辑文件。计划及修订会被记录，同时保存批准人的信息。常规变更由工程师批准，高风险变更交给技术负责人或架构师。

#### 衡量方式

领先指标包括一次实现后即可合并的变更比例，以及从计划批准到 PR 合并所用的时间。所需数据可以放在 PR 元数据中。

滞后指标包括每项变更的返工轮数，以及合并后的代码差异仍与 `plan.md` 保持一致的比例。这些数据同样可从 PR 元数据获取。

### 6.2 Claude Code 自动模式

Claude Code 也可以在自动模式下运行。工程师批准并充分调整计划后，Claude 可以直接应用每项修改，不再逐次请求编辑许可。

随着后续方案中的约束逐渐成熟，包括经过优化的 `CLAUDE.md`、编码政策的 Skills、阻止不安全操作的 Hooks，以及 Claude 能自行运行的测试套件，自动接受会成为常规工作的默认选择。适合这一模式的工作应有明确的 `spec.md`、较小的影响范围，并且已有测试覆盖。

用户的注意力会从盯着智能体执行每次编辑，转移到较长时间的自主会话结束后评审产物。结合 worktree 使用时，自动接受模式还支持个人和团队并行工作，也是第六阶段自主运行 SDLC 并闭合循环的基础。

### 6.3 旧系统与唯一事实来源

这一原则适用于流程生成的每一种产物。

现有 SDLC 很可能已经在其他系统中记录产物。工作项可能位于 Jira，需求保存在具备监管追踪能力的工具中，设计在 Figma，变更审批交给变更委员会。审计人员和监管方已经接受这些系统，其他团队也依赖它们，因此很难直接替换。AI 原生 SDLC 必须适应现有环境。

迁移期间，应为每种产物指定一个唯一事实来源，其他系统只保存副本或原始记录的链接。不同产物可以选择不同方案。

1. 以代码库为唯一事实来源。Markdown 产物是权威记录，旧系统引用具体提交中的文件。对于工程驱动的组织，这是较简洁的配置，所有记录位于同一个工具并使用同一套时间戳。
2. 以旧系统为唯一事实来源。Jira、ServiceNow 或需求工具保存权威记录，Markdown 产物只是工作副本。Claude 在会话开始时读取正式记录，并在生成规范或计划的同一会话中通过 MCP 连接器把结果写回。
3. 至少建立双向链接。所有产物标注记录 ID，所有旧系统记录保存 Markdown 文件的 commit SHA。迁移初期可以从这里开始，但需要接受暂时存在两个事实来源。

旧系统和 Markdown 优先的系统可以共存，前提是两者之间存在链接，或者其中一个被明确指定为唯一事实来源。

### 6.4 使用 `CLAUDE.md` 保存团队工作知识

`CLAUDE.md` 为 Claude 提供新成员入职时需要的上下文，涵盖约定、命令、架构和团队最常见的错误。过去存在于成员脑中和 Wiki 上的知识，转为智能体每次会话开始都会读取的文件。整个团队共同维护它，每当出现错误就继续调整。

#### 前置条件

无。

#### 基础设施

一个代码库、已经安装的 Claude Code，以及一名熟悉代码库的工程师。

#### 实施步骤

1. 在代码库中运行 `/init`，Claude 会根据发现的内容生成初始 `CLAUDE.md`。
2. 删减生成文件，只保留新成员第一天需要知道的内容，包括构建、测试和 lint 命令，重要约定，以及 Claude 经常犯错的地方。
3. 把 `CLAUDE.md` 提交到代码库根目录，让整个团队共享同一版本，并像评审代码一样评审它的变更。
4. 建立一条工作规则。同一种错误出现两次，就把修正方式写入 `CLAUDE.md`。
5. 将文件控制在一页以内。Claude 会在会话开始时读取全部内容，过期信息只会无谓占用上下文。

#### CLAUDE.md 示例

```markdown
# 支付服务

## 命令

- 构建：make build
- 测试：make test（单元测试），make itest（集成测试，需要 Docker）
- Lint：make lint（CI 中也会运行，推送前修复）

## 约定

- Java 21，Spring Boot 3。不要新增 Lombok。
- 金额一律使用 BigDecimal，禁止使用 double。
- 每个端点都需要在 src/itest 中添加集成测试。

## 架构

- api/ 保存 REST 控制器，core/ 保存领域逻辑，adapters/ 与外部系统通信。
- Kafka 事件定义在 schemas/ 中，禁止编辑生成的类。

## Claude 容易出错的地方

- 不要升级依赖版本，依赖由平台团队负责。
- 旧版 v1/ 已冻结，所有变更进入 v2/。
```

#### 治理事项

`CLAUDE.md` 受到版本控制，因此智能体遵循的指令可以接受评审和审计。团队约定通过该文件统一应用，所有修改记录在 git 历史中，并由代码负责人在 PR 中批准。

#### 衡量方式

领先指标是 Claude 重复犯下本应由 `CLAUDE.md` 避免的错误的频率，相关修正和文件修改应在 git 历史中跟踪。

滞后指标是新成员从加入团队到合并首个 PR 所用的时间，可从 PR 历史中获取。

### 6.5 使用 Skills 保存组织知识

Skills 能让组织知识直接参与工作。指令明确、受版本控制、可以广泛应用，并在政策变化时集中更新。经验原则是，需要一致执行的组织知识应写成 Skill；只属于单个代码库的内容放进 `CLAUDE.md`，一次性内容则留在提示词中。

#### 前置条件

没有硬性要求。拥有 `CLAUDE.md` 会有所帮助，因为它把智能体工作知识留在代码库中，但 Skill 并不依赖该文件。

#### 基础设施

选择一项有明确负责人与书面唯一事实来源的政策。

#### 实施步骤

1. 选择一项目前执行不一致的知识，可以是安全标准、API 设计约定或品牌规则。
2. 将其写成 Skill。Skill 是一个文件夹，其中包含 `SKILL.md`。文件的 frontmatter 说明何时触发，正文说明该做什么。工程师根据政策负责人的权威材料编写，可以请 Claude 协助。
3. 将 Skill 放在代码库的 `.claude/skills/<name>/` 中，使其随代码分发，或者通过插件向整个组织分发。
4. 测试 Skill 能否触发。用不同方式要求 Claude 完成相关任务，确认每次都会加载 Skill。
5. 政策变化时同步修改 Skill，并请政策负责人批准变更。
6. 工程师在下一次会话中会自动使用新版本。

#### Skill 示例

```markdown
---
name: secure-api-review
description: 应用 API 安全标准。创建或修改面向外部的端点、评审 API 代码或生成 OpenAPI 规范时使用。
---

# 安全 API 评审

创建或修改 API 端点时遵守以下规则。

1. 身份认证。每个端点都需要网关 JWT，除 /health 外不得有匿名路由。
2. 输入校验。依据 OpenAPI schema 校验请求体，并拒绝未知字段。
3. 审计。每个会改变状态的端点都应发出审计事件，包含 actor、action、entity 和 timestamp。
4. 数据分类。schema 中标为 pii 的字段不得出现在日志或错误消息中。

运行 scripts/check-endpoints.sh，并在总结中附上输出。
```

#### 治理事项

Skill 是一种建议性控制。它提高 Claude 在编写代码时应用政策的概率，但不能强制每次会话都遵守。必须始终成立的政策还需要确定性机制，例如阻止操作的 Hook，或者在 PR 阶段重新检查政策的评审流程。Skill 用来显著减少违规，Hook 用来让违规接近不可能发生。

Skill 的调用记录在会话追踪中，政策负责人像评审代码一样评审 Skill 变更。

#### 衡量方式

领先指标是从政策负责人批准政策变化，到更新后的 Skill 合并所用的时间，可从 Skill 文件夹对应的 PR 中获取。

滞后指标是 PR 评审中引用该政策的问题数量。Skill 在代码编写时正确应用政策后，这个数字应趋近于零。若没有下降，说明 Skill 没有触发，或者其内容已经偏离正式政策。

### 6.6 使用 Hooks 充当构建期约束

Skill 是建议性控制，Hook 则是背后的确定性执行层。Claude 在实现期间的大部分动作都是文件编辑和 shell 命令，因此 Hooks 在构建阶段触发最频繁。

构建阶段的 Hooks 可以完成以下工作。

1. 阻止编辑受保护路径，例如生成的类或已冻结的软件包。
2. 每次编辑文件后运行格式化工具和 linter，避免格式偏差积累。
3. 阻止凭据进入代码差异。

任何必须无条件成立的政策，都应在 Skill 之外增加 Hook。Hook 会在每次匹配动作时运行，因此构建期 Hook 应当快速，并限制在刚刚发生变化的文件范围内。完整测试套件等较重检查应放到提交或 PR 阶段。

要求人工批准的 Hook 应放在第五阶段的关卡中。构建期间弹出审批请求，会让人在所有并行会话的关键路径上重新成为瓶颈。

### 6.7 并行会话与子智能体

一名工程师可以同时推动多条工作流。

并行会话是另一套完整的 Claude Code 实例，在自己的 git worktree 中处理独立任务。各个会话彼此完全隔离，唯一共享的是负责引导它们的工程师。

子智能体运行在单个会话内部，是拥有独立上下文窗口和工具限制的范围化助手。它适合在多个任务中反复出现的工作，例如验证应用是否按预期运行。

并行会话增加一名工程师同时进行的任务数量，子智能体则让每个会话始终聚焦自己的任务。工程师负责引导并评审所有结果。

传统流程中，一名工程师一次处理一项任务，一天或一周内有相当多的时间花在等待构建、测试和评审。等待时切换到别的任务虽然可行，但上下文切换带来的负担让很多人不愿这样做。

AI 原生流程中，一名工程师同时运行多个 Claude 会话，每个会话在独立 worktree 中处理自己的任务。重复工作被固化为拥有独立上下文和工具限制的子智能体。工程师的职责转向编排，最终转向建立并监控自主循环。

#### 前置条件

需要 `CLAUDE.md`，因为所有会话都会读取它。第四阶段的反馈循环也很有帮助，会话能自行验证结果后，工程师所需的监督会减少。

#### 基础设施

需要 git 仓库，因为任务隔离依靠 worktree。还要调整权限设置，让会话执行组织认定安全的命令时不必等待审批提示。

#### 实施步骤

1. 工程师根据计划模式生成的方案，将工作拆成修改不同文件的任务。共享文件的任务应放在同一会话中顺序执行。
2. 每个并行任务使用独立 worktree。例如在一个终端运行 `claude --worktree feature-auth`，在另一个终端运行 `claude --worktree fix-rate-limit`。worktree 是位于独立分支的单独检出，可以避免会话修改同一文件时发生冲突。
3. 从两个或三个会话开始较为合理。实际数量上限取决于一个人能够认真评审多少条工作流，只有评审跟得上时才增加会话。
4. 将重复工作定义为子智能体，文件放在 `.claude/agents/`。每个定义包含名称、使用时机说明和允许访问的工具。示例包括在主智能体完成后清除不必要复杂度的代码简化器，运行应用并检查行为的验证器，以及探索代码库并回报结果、避免主上下文被大量细节占满的研究助手。将定义提交到 git，供整个团队共享。

#### 子智能体示例

```markdown
---
name: verifier
description: 在会话报告完成之前运行应用并检查变更是否正常工作
tools: Bash, Read
---

使用 make run 启动应用。验证本次修改涉及的行为，以及距离最近的两个相邻流程。报告运行了什么、观察到什么，以及所有不符合 plan.md 的行为。只报告，不要修复。
```

#### 治理事项

会话越多，产出也越多，因此控制措施需要来自代码库内的统一配置。Hooks 和权限设置会应用到所有会话，每个会话的动作都会记录，并归属于启动它的工程师。

#### 衡量方式

领先指标包括评审质量保持稳定时，每名工程师同时运行的会话数量，以及一天中用于引导而非等待的时间比例。并发数据可以从 OpenTelemetry 导出中统计。

滞后指标是每名工程师每周合并的变更数量，应结合 PR 历史中的返工率一起阅读。

## 7. 第四阶段 测试

每个会话都应在人工看到结果之前检查自己的工作。引导智能体的配置也需要像智能体编写的代码一样接受回归测试。

### 7.1 为 Claude 建立反馈循环

始终为 Claude 提供验证自己工作的方式，可以是测试、构建结果或截图差异。会话在工程师查看结果前自行检查并修正错误。

反馈循环与第三阶段的验证子智能体不是同一概念。反馈循环会在整个任务过程中反复运行，次数取决于工作需要。验证子智能体则是封装最终检查的一种方式，在主会话认为工作已经完成后，用全新的上下文窗口执行检查。这样可以避免最终判断受到编写代码时所作假设的影响。

传统流程很晚才能知道代码是否正常工作。CI 可能几分钟后才有结果，测试人员可能几天后才反馈，生产问题甚至要几周后才出现。智能体生成代码时，过晚的信号会迫使人检查其全部产出，人也会随之成为瓶颈。

AI 原生流程为会话提供自查手段。运行测试、运行构建或生成截图，Claude 持续迭代直到检查通过，因此工程师拿到的结果已经经过验证。建立反馈循环由启动会话的工程师负责。

#### 前置条件

无。

#### 基础设施

需要可以用单个命令在本地运行的测试套件和构建流程。对于界面工作，让 Claude 看到结果非常关键，可以使用浏览器工具，或者通过 MCP 接入截图工具。

#### 实施步骤

1. 如果当前验证工作需要多条命令和特定环境知识，将它们封装成 `make test` 或 `npm test` 之类的单一目标，并确保失败时返回非零退出码。
2. 在 `CLAUDE.md` 的 Commands 部分列出每条命令，并给出健康输出示例。
3. 提供可量化的目标，让 Claude 无需询问即可检查结果。例如 `test_status.py` 中的所有测试通过、截图与随附原型一致，或者端点返回 200 且包含新字段。
4. 修复缺陷时先编写失败测试。要求 Claude 把缺陷复现为测试，运行并确认测试因预期原因失败，再提交该测试。随后要求 Claude 在不修改测试的前提下让测试通过，并用最后一步的测试文件 Hook 强制执行这项限制。修复前已经存在且智能体无法改写的测试，能证明缺陷确实消失。
5. 界面工作使用视觉检查闭合循环。为 Claude 提供浏览器或截图工具以及设计原型，让它执行实现、截图、比较和调整。通常需要两到三轮，每轮结果都应有所改善。
6. 把验证写进完成标准。相关指令放在 `CLAUDE.md` 中，要求报告任务完成前运行测试并展示输出。
7. 反馈循环本身也需要保护。负责修复代码的智能体不能削弱检查代码的机制。可以用 Hook 阻止修复任务编辑测试文件，也可以在评审中检查代码差异并拒绝任何测试修改。

#### CLAUDE.md 验证配置示例

```markdown
## 验证工作

- 构建：make build，必须以 Build succeeded 结束
- 测试：make test，所有测试通过，禁止跳过或删除失败测试
- Lint：make lint，警告数为零

报告任务完成前运行以上三项，并粘贴输出。
如果测试失败，修复代码，不要修改测试。
```

#### 治理事项

组织可以通过 Hooks 强制执行两项要求，包括任务报告完成前必须验证，以及修复期间禁止智能体编辑测试文件。

证据来自 `make test` 的原始输出、构建日志或 Claude 生成并粘贴的截图差异，因此由工具链直接产生。

这些证据记录在会话记录中，再由 OpenTelemetry 导出到组织的可观测性系统，同时也出现在 PR 检查结果中，供评审者和后续审计人员查看。

代码负责人在 PR 中批准变更。机械验证证据已经附上后，评审者可以集中判断意图和风险。

#### 衡量方式

领先指标是智能体编写的变更首次通过 CI 的比例，现有 CI 系统通常已经能提供该数据。

滞后指标包括每个 PR 的评审时间，以及事故跟踪系统中的变更失败率。测试接手过去由评审者发现的问题后，评审时间应当下降。

### 7.2 在 CI 中持续运行评估

评估是 AI 原生流程中对应阶段关卡式 QA 的机制。实际形式是一套在智能体配置发生变化时运行的评估集。更换模型或改写提示词后，评估集会判断智能体能否继续按照同一标准完成工作。

评估集需要持续维护。模型改进后，一些过去能区分质量的用例会失去作用，持续监控中出现的新问题则应加入评估。

根据具体场景，有些团队可以按照固定周期离线运行评估，无需每次变更都运行。以下步骤针对持续评估。

#### 前置条件

第三阶段的 `CLAUDE.md` 和本阶段的反馈循环。

#### 基础设施

能够非交互运行 Claude Code 的 CI，以及拥有足够评估预算的 API Key。

#### 实施步骤

1. 平台工程师从近期工作中收集 20 到 50 个真实任务，并记录每个任务的预期或已接受结果。
2. 将每个任务写成评估用例，包括提示词和定义可接受结果的检查，例如测试通过、lint 无问题、行为未变化和政策得到遵守。
3. 评估集在 CI 中按计划非交互运行，并在 `CLAUDE.md`、Skills 或 Hooks 发生任何变化时运行。这些配置会引导智能体，应接受与代码相同的回归测试。
4. 依据结果设置配置变更关卡。Skill 变更导致通过率下降时，应在合并前接受评审。
5. 每次生产事故都应由事故负责团队写成评估用例，并永久保留在评估集中作为回归测试。

#### CI 工作流示例

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

#### 治理事项

评估为 QA 提供了能跟上智能体产出速度的关卡。通过率阈值作为合并检查强制执行，每次运行都会记录，便于比较长期结果。拥有配置变更的团队负责批准变更。

#### 衡量方式

领先指标包括评估通过率的长期变化，以及生产事故转成永久评估用例所需的时间。评估集每次运行都会报告通过率。

滞后指标是 CI 捕获的回归问题与生产环境发现的回归问题之比，可以结合事故跟踪系统统计。

## 8. 第五阶段 部署

评审在两个方向上运行，治理在智能体采取行动时执行。智能体可以完成生产关卡之前的所有工作，但不能自行越过关卡。

### 8.1 将 AI 加入 PR 评审循环

Claude 同时提供和接受评审。它依据组织政策评审传入的 PR，也会处理自己所开 PR 中的评审意见。工程师因而可以把人工评审集中在行为上，判断变更是否符合意图以及风险是否可接受。

传统流程的评审能力按照人类产出配置。PR 等待评审者逐行阅读，评审质量会随着评审者负载变化，作者不断跟进，积压也持续增加。

AI 原生流程让所有 PR 接受相同的一组评审，并按严重程度排列问题。人的注意力上移到更高层级，判断变更是否实现计划意图，以及风险能否接受。

#### 前置条件

第三阶段更新后的 `CLAUDE.md`。如果评审需要执行书面政策，还需要 Skills 和已经定义的子智能体。

#### 基础设施

代码库需要安装 Claude 集成。可以由管理员启用托管的 Code Review 服务，目前处于研究预览阶段，也可以在自己的 CI 中运行 `claude-code-action`。如有需要，模型调用可以通过 AWS Bedrock、Google Vertex 或 Microsoft Foundry 完成。最好同时启用要求代码负责人批准的分支保护策略。

#### 实施步骤

1. 托管的 Code Review 服务最容易启动，由管理员启用并选择代码库。需要控制流水线或希望 API 调用通过组织自己的云协议时，可以在 CI 中运行 `claude-code-action`。
2. 技术负责人在代码库根目录编写 `REVIEW.md`，按组织关注的方面划分评审轮次，包括缺陷和逻辑错误、安全与漏洞，以及变更是否符合 `spec.md`、`plan.md` 和设计原则。文件还要定义 Important 与 Nit 的区别，并列出应忽略的内容。
3. 技术负责人设置人工阈值。智能体发现的问题本身不会批准或阻止 PR，分支保护仍要求代码负责人批准。希望依据问题阻止合并的平台工程师，可以读取检查结果发布的机器可读严重程度统计。
4. 评审者或作者在评审评论中标记 `@claude` 后，Claude 会处理意见并推送修复。PR 讨论串同时记录请求和修改。这个修复循环通过 `claude-code-action` 运行。使用托管服务时，评论 `@claude review` 会请求重新评审。对于 Claude 自己创建的 PR，还可以让它持续跟进直到具备合并条件。团队通常把这套循环封装成自定义斜杠命令，反复检查未解决评论和失败检查，修复并推送，直到 PR 全部通过，只等代码负责人批准。
5. 评审发现会反馈到 `CLAUDE.md`。同一种错误第二次出现时，在本次评审中把修正写入 `CLAUDE.md`。后续评审会读取该文件，从下一份 PR 起捕获同类问题。评审还应指出代码变更何时使 `CLAUDE.md` 过期。
6. 技术负责人每月优化设置。对评审发现进行评分，用于改进评审者，并在 `REVIEW.md` 中限制 Nit 数量。生成路径和 CI 已经执行的检查应排除在外。

#### REVIEW.md 示例

```markdown
# 评审指令

## 评审轮次

运行三轮评审，并为每项发现标注所属轮次。

- 缺陷。逻辑错误、失效边界情况和隐蔽回归。
- 安全。注入风险、身份认证缺口和日志中的个人身份信息。
- 合规。变更符合 spec.md、plan.md 和我们的设计原则。

## Important 的定义

只有会破坏行为、泄露数据或违反政策的问题才标记为 Important。
样式和命名属于 Nit。

## 限制 Nit 数量

每次评审最多报告五项 Nit，其余只汇总数量。

## 不要报告

src/gen/ 下的生成文件，以及 CI 已经执行的检查。
```

#### 治理事项

职责分离仍然保留，因为编写代码的智能体无法批准自己的变更。`REVIEW.md` 中的评审政策会应用到所有 PR，发现、修复、评分和批准都记录在 PR 历史中，因此 PR 本身就是审计记录。最终批准由人通过分支保护完成，并参考智能体给出的发现。

#### 衡量方式

领先指标包括第一次评审所需的时间，目标应缩短到几分钟，以及无需人工修改分支即可解决的评审评论比例。数据直接保存在 Git 中。

滞后指标是合并前捕获的缺陷和漏洞，与逃逸到生产环境的问题之比。数据来自 PR 历史和事故跟踪系统。

### 8.2 使用 Hooks 充当审批关卡

构建阶段的 Hooks 充当约束，无需人工参与即可允许或阻止动作。Hook 也可以发起询问，暂停动作，直到指定人员批准，这正适合发布关卡。

这项方案放在部署阶段，因为发布关卡是最直观的场景。Hooks 并不局限于部署，它们会在 Claude 执行动作的任何阶段运行。例如，在构建阶段，Hook 可以阻止没有变更工单的迁移文件和基础设施编辑；在测试阶段，它可以阻止智能体在修复任务中编辑测试文件。

#### 前置条件

无。

#### 基础设施

一份书面清单，列出变更流程要求的所有审批。

#### 实施步骤

1. 工程管理层与变更管理和合规团队共同列出必须保留的人工审批关卡，例如变更管理签字、发布授权和受保护路径编辑。
2. 平台工程师将每道关卡实现为 Hook。脚本在 Claude 执行动作之前运行，可以允许、询问或阻止。
3. 团队 Hooks 放在纳入 git 的 `.claude/settings.json` 中。不可协商的 Hooks 放在由平台或 IT 管理员控制的托管设置中，个人工程师无法关闭。
4. 阻止操作时要说明原因。Claude 的输出应显示阻止原因和获得批准的方式。

#### Hook 配置示例

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh"
          }
        ]
      }
    ]
  }
}
```

#### 生产关卡脚本示例

```bash
#!/bin/bash
# 生产部署需要指定发布授权
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2 # 退出码 2 会阻止操作，消息会传给 Claude
  fi
fi
exit 0
```

#### 治理事项

Hooks 就是审批关卡。每次操作、每名用户都受到同一关卡条件约束。允许和阻止决定会与时间戳一起记录。关卡还定义何种记录算作批准，例如已批准的变更工单或发布经理签字。

### 8.3 受监管企业的托管设置示例

以下配置由平台团队通过 MDM 或管理控制台部署，工程师无法编辑或覆盖。

```json
{
  "permissions": {
    "deny": [
      "Read(.env*)",
      "Read(./secrets/**)",
      "WebFetch",
      "Bash(curl *)",
      "Bash(wget *)"
    ],
    "allow": [
      "Bash(git *)",
      "Bash(make build)",
      "Bash(make test)",
      "Bash(make lint)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": [
        "git.internal.example.com",
        "registry.npmjs.org"
      ]
    },
    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" }
      ]
    }
  },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true,
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
    {
      "source": "github",
      "repo": "example-corp/approved-plugins"
    }
  ],
  "requiredMinimumVersion": "2.1.193"
}
```

各项配置提供的控制效果如下。

1. `permissions.deny` 避免秘密进入智能体上下文，并通过工具阻止任意网络访问。`permissions.allow` 预先批准安全的内部循环，避免拒绝列表造成频繁审批提示。
2. `disableBypassPermissionsMode` 与 `allowManagedPermissionRulesOnly` 共同确保工程师、项目文件和命令行参数都无法扩大权限。
3. `sandbox` 补足权限系统无法覆盖的部分。工具层禁止 WebFetch，并不能阻止 shell 命令访问网络。操作系统层的域名允许列表会直接阻止未授权网络流量。
4. `failIfUnavailable` 与 `allowUnsandboxedCommands` 让沙箱成为强制关卡。沙箱无法初始化时，Claude Code 会拒绝启动；命令在沙箱内失败后，也不能转到沙箱外重试。
5. `credentials` 补足拒绝规则留下的缺口。`permissions.deny` 管理 Claude 的文件工具，但沙箱内的 shell 命令默认仍可能读取 `~/.ssh` 或 `~/.aws/credentials`。这部分配置禁止读取这些位置，并从每个沙箱命令的环境变量中移除指定秘密。
6. `allowManagedHooksOnly` 确保只有本方案中的审批关卡可以运行，本地配置无法增加或替换 Hooks。
7. `disableSideloadFlags` 与 `strictKnownMarketplaces` 确保工程师机器上的 Skills、Agents、Hooks 和 MCP Server 都来自组织批准的插件市场，不允许从个人主目录加载。
8. `allowManagedMcpServersOnly` 把智能体可用工具限制为平台团队管理的允许列表。
9. `requiredMinimumVersion` 阻止低于批准版本的客户端启动，确保控制措施由组织已经评估的构建版本执行。

以上配置应作为按实际情况调整的起点，不宜直接照搬。每项禁止规则都会牺牲一部分能力，合适的平衡取决于代码库的数据分类。

#### 衡量 Hooks

领先指标是每道审批关卡的等待时间。每次 Hook 决定都会通过 OpenTelemetry 导出，包含时间戳和允许或阻止结果，因此可以分别看到各关卡的耗时。

滞后指标是引入 Hooks 前后到达生产环境的关卡违规数量，可从事故跟踪系统获取。

### 8.4 CI/CD 集成与部署

在 CI/CD 流水线中非交互运行 Claude Code。执行过程放在沙箱中，让长期运行的智能体保持安全。通过 MCP 集成提供部署能力，并在智能体真正需要回滚之前反复演练回滚路径。

传统流水线运行确定性脚本，凡是需要判断的工作都要等待人工，例如判断偶发测试、编写变更日志或分析构建失败原因。部署和回滚则依靠人在压力下按照操作手册执行。

AI 原生流水线让 Claude 在沙箱中使用范围化凭据，以非交互方式执行需要判断的步骤。部署工具通过 MCP 提供给智能体，因此编写并测试变更的工作流也可以完成发布和回滚，同时遵守组织为各环境定义的关卡。

#### 前置条件

先让 Claude 进入 PR 评审循环，并将 Hooks 设置为审批关卡。自动化加速流程之前，关卡必须已经存在。

#### 基础设施

需要安装 `claude-code-action` 的 CI 平台，或者任何能够调用 `claude -p` 的 Runner。模型可以通过 API 访问；必须让流量留在组织云协议内时，也可以通过 Bedrock、Foundry 或 Vertex 访问。还需要面向部署目标的 MCP Server，以及没有长期生产凭据的智能体任务沙箱配置。

#### 实施步骤

1. 平台工程师先从只读判断任务开始。在流水线任务中使用 `claude -p` 分析失败构建、总结偶发测试或起草变更日志。
2. 在现有关卡后加入写入任务，例如修复 lint、更新生成文档，或者通过 `@claude` 处理评审意见。智能体写入的所有内容都通过受分支保护的 PR 提交，没有直接推送主分支的路径。
3. 在沙箱中执行。智能体任务运行于受网络策略约束的容器，使用短期范围化令牌，默认不持有生产凭据。
4. 通过 MCP 提供部署能力。部署、状态查询和回滚成为按环境限定的工具，智能体的部署权限因此表现为允许列表，不是带凭据的任意 shell 脚本。
5. 按环境划分自主程度。开发环境中，智能体可以自由部署。生产环境中，智能体准备发布，由发布经理授权，Hook 强制执行生产关卡。预发布环境位于两者之间。
6. 回滚应是流水线中演练最充分的路径。它需要是一条智能体可以运行的命令，并在预发布环境定期演练。第六阶段会在控制带越界时调用回滚，因此必须预先证明有效。

#### 流水线步骤示例

```yaml
- name: Triage failed build
  if: failure()
  run: >
    claude -p "Read the build log at out/build.log. Identify the most
    likely cause, say whether the failure looks flaky or real, and write a
    three-line summary for the PR thread." >> triage.md
```

#### 治理事项

治理原则是允许智能体一直行动到生产关卡，但不能越过它。以下控制措施用于执行这项原则。

1. 分支保护让智能体写入的所有内容变成 PR，不存在直接进入主分支的路径。
2. 生产部署 Hook 会阻止发布，直到指定发布经理授权。每次非交互运行都使用智能体自己的身份，因此流水线日志可以区分智能体的动作与触发任务的工程师所做的动作。
3. 各环境的权限等级决定智能体在到达关卡前可以完成多少工作。

#### 衡量方式

领先指标是无需呼叫人工即可完成分析的流水线失败比例，可从 CI/CD 日志中获取。

滞后指标使用 DevOps Research and Assessment，也就是 DORA 指标。CI 系统和部署工具通常已经会输出这些数据。

## 9. 第六阶段 维护

循环在这里闭合。触发器可以在没有人介入调用路径的情况下启动 Claude，诊断结果再以 `intent.md` 形式回到流水线。

### 9.1 维护与闭合循环

此前各阶段都要求人启动第一步。维护阶段开始让 Claude 自主运行，以闭合整个循环。

持续运行的监控智能体可以在缺陷工单出现后创建 `intent.md`，随后流经需求、计划、构建、测试和评审阶段。第六阶段以无界面模式运行，阶段之间设置独立的置信关卡。关卡可以是确定性检查，也可以是负责对抗性评审的智能体，用于决定上一阶段的输出继续前进，还是升级给人处理。

传统维护是被动阶段。每张工单或每次事故都要等待人介入并重新启动流程。凌晨三点的告警可能被错过，工单可能长时间留在待办列表中，复盘行动也可能因为新的紧急问题而无法进入代码库。

AI 原生维护由控制带越界、工单、频道消息或计划任务等触发器启动 Claude，调用路径中不需要人。Claude 负责诊断，只能通过受关卡控制的路径行动，并把发现写成 `intent.md`，随后进入前面各阶段。人负责分流和评审，无需亲自启动流程。

### 9.2 通过控制带闭合循环

确定性脚本持续监控生产环境，在控制带越界时调用 Claude。监控越界是自主循环的一种典型实现。来自其他频道的工作会在本阶段末尾的 Claude Tag 部分说明。

#### 前置条件

需要 `intent.md`，为循环提供重新开始时的结构化输出。还需要已经由 Claude 加速的 PR 评审、把 Hooks 用作动作边界，以及 CI/CD 中可靠的回滚路径。最高自主等级会直接调用这条回滚路径。

#### 基础设施

需要检测脚本可以查询的指标存储，例如 Prometheus、CI 系统 API 或同类系统；代码库读取权限；在 CI 中非交互运行 Claude Code 的方式。接收 Webhooks 的服务也可以使用 Agent SDK。

#### 实施步骤

1. 服务负责人或平台工程师选择一项拥有稳定滚动基线的指标，例如 CI 测试失败率、部署后 5xx 比例或 PR 周期时间。
2. 编写检测脚本。通常在滚动窗口内计算均值和标准差，并使用 Western Electric 等规则，让控制带既能发现尖峰，也能捕获缓慢漂移。脚本纳入版本控制并编写单元测试。检测过程完全确定，不使用模型。
3. 在受版本控制的配置中定义响应等级。下方 `bands.yaml` 中，1σ 只记录日志，2σ 以只读方式调用 Claude 进行诊断，3σ 允许 Claude 行动，但只能创建进入评审关卡的 PR，或者触发预先批准的操作手册。
4. 触发层可以是 GitHub 或 GitLab 的计划工作流、现有监控系统发出的 Webhook，或者内网中的 Cron Job。Claude 以无状态方式运行，可以作为 CI Runner 上的非交互步骤，也可以作为沙箱容器中的 Agent SDK 服务。由于运行无状态且非交互，一轮循环可以在无人启动的情况下开始并结束。
5. 智能体按照第一阶段格式把诊断写成 `intent.md`，其中包含异常及证据、期望结果、受影响系统和未决问题。随后，这项发现会像其他工作一样进入流水线。
6. 服务负责人或值班工程师处理队列，把涉及产品的发现转给产品负责人，并决定立即修复、排期或忽略。忽略记录用于调整控制带并降低噪声。
7. 修复发布后，为事故增加一项评估用例，确保以后能够防止同类问题。

#### bands.yaml 示例

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma:
    { action: diagnose, tools: "Read,Grep,Bash(gh run view *)" }
  3sigma:
    { action: propose, routes: [pull_request, runbook:rollback-deploy] }
```

#### 治理事项

各响应等级边界由受版本控制的配置执行，权限和托管设置会阻止生产访问。所有调用、发现和分流决定都会与时间戳一起记录。服务负责人负责分流并批准发现，后续变更通过常规 PR 评审关卡，智能体可触发的操作手册则提前得到批准。

#### 衡量方式

领先指标是从控制带越界到分流队列中出现 `intent.md` 所用的时间，与过去从事故发生到产生复盘行动的时间比较。检测脚本日志保存越界时间戳和事故等级。

滞后指标包括最终形成合并修复的发现比例，以及同类事故重复出现的次数。修复不断加入评估用例后，重复事故应逐渐减少。

#### 示例

1. CI 测试失败率越过 3σ 时，智能体隔离偶发测试或创建回滚 PR，最终由评审关卡决定。
2. 部署窗口内的部署后 5xx 比例越过 3σ 时，智能体触发现有回滚流水线。
3. PR 周期时间触发漂移规则时，智能体为工程管理层编写报告。这也证明同一套机制可以用于流程指标和生产指标。

检测始终保持确定性。只有控制带越界后才调用 Claude，响应等级决定它可以采取什么动作。

### 9.3 定期扫描代码库

安全扫描只说明特定模型在特定时点看到的代码库状态，代码和模型都会变化。代码每周都在修改，新一代模型也可能发现上一代遗漏的漏洞。AI 原生方案按计划运行扫描，无需人工发起，并把发现送入与其他代码变更相同的关卡。

Claude Security 是托管的定期扫描产品。连接 GitHub 仓库后，扫描会在 Anthropic 基础设施中使用 Claude Mythos 5 运行。每项发现都会先接受验证，再附上置信度。建议补丁可以在 Claude Code 网页版中评审和应用。组织无需自行获得模型访问权限也能得到扫描结果。

传统安全扫描通常发生在发布或审计之前。报告进入跟踪系统，团队手动处理积压，直到下一次扫描。两次扫描之间写入的代码，只能依赖 PR 评审覆盖。

AI 原生扫描按计划对每个已连接代码库运行，并使用当前能力最强的模型。每项发现都会在人工阅读前验证。处理方式与控制带越界相同。能在一个 PR 中解决的问题进入评审关卡，范围更大的问题写成 `intent.md`。安全覆盖日期取自最近一次运行，不再停留在首次扫描时间。

#### 前置条件

需要第五阶段的 PR 评审关卡和审批 Hooks，使发现像其他变更一样接受评审。超过单个 PR 范围的问题还需要第一阶段的 `intent.md` 格式。

#### 基础设施

Claude Security 目前以公开测试形式提供给 Claude Enterprise 组织。目标代码库需要位于云托管的 github.com，并安装 Anthropic GitHub App；同时启用 Claude Code 网页版和 Extra Usage，设置支出上限，为执行扫描的人分配 Premium 席位，并由管理员在 `claude.ai/admin-settings/claude-code` 中开启功能。扫描按 Mythos 5 用量计费，因此支出上限应与代码库规模和数量相匹配。

#### 实施步骤

1. 安全负责人连接代码库，并按仓库、服务或团队组织成项目，让每项发现从一开始就有明确归属。
2. 首先完整扫描最关键的代码库，包括过去已经由其他工具或旧模型扫描过的仓库。把第一次扫描当作基线，它很可能会在过去被认为干净的代码中发现问题。
3. 为每个项目设置计划。正在积极开发的服务可以每周运行一次。代码库较大或内容混杂时，可以限定到特定目录或分支。
4. 结合置信度处理发现。忽略时要记录原因，使决定可追踪，也避免同一问题在下次运行时再次被当成新发现。
5. 对范围明确的问题，在 Claude Code 网页版中打开建议补丁，完成评审，再像其他变更一样进入 PR 评审关卡。提出修复的智能体没有批准权限。
6. 对超过一个补丁范围的问题，例如架构弱点或跨服务重复模式，按照第一阶段格式写成 `intent.md`，从规划阶段重新开始。
7. 修复发布到生产环境后，把该漏洞类别加入持续评估集，使引导智能体的配置从此接受这一类别的测试。
8. 将发现导出为 CSV 或 Markdown，也可以使用 Webhooks，让组织现有的跟踪和审计系统继续充当审计人员认可的唯一事实来源。

#### 治理事项

扫描在组织的管理控制下运行。连接哪些代码库、谁拥有扫描席位和支出上限都由管理员集中设置。每项发现都有验证结果和置信度，每项忽略都有理由，因此扫描历史可以审计发现了什么、修复了什么，以及哪些风险经过明确判断后被接受。

修复通过 PR 评审关卡和分支保护进入生产环境，扫描本身不能直接发布代码。Claude Security 用于补充现有静态分析和依赖扫描。确定性检查继续留在 CI 中，模型驱动扫描负责发现这些检查不擅长处理、依赖上下文判断的漏洞。

#### 衡量方式

领先指标包括已经设置定期扫描的已连接代码库比例，以及从报告发现到补丁进入 PR 评审关卡所用的时间。数据来自扫描历史和 PR 元数据。

滞后指标包括定期扫描发现的漏洞与生产环境或外部报告发现的漏洞之比，以及经过多轮扫描的代码库中每次扫描发现数量的变化趋势。随着修复和评估积累，发现数量应逐渐下降。

### 9.4 使用 Claude Tag 值班

事故也可能从 Slack 或 Teams 等工作沟通软件传入。晚上十点，事故频道里可能出现一条要求紧急修复的消息。Claude Tag 目前在 Slack 中提供公开测试，它让 Claude 以自己的身份成为频道成员，每起新事故因此都能立即得到第一响应。响应过程也会成为循环的一部分，为以后处理事故留下可读取的记录。

对话和组织知识留在频道中，频道里的任何人都可以引导响应并授权行动。团队成员可以实时测试假设、探索方案和调查问题，频道历史也增强了可审计性。通过 MCP，Claude 可以确认指标已经恢复到基线并在讨论串中回复，还会将事故复盘写入受版本控制的经验文件，供后续调查读取。

Claude Tag 也可以接收其他工作。通过 MCP 在工单中标记 Claude，或直接在频道中提出请求后，Claude 会采用同一方式分流。范围小且边界清晰的修复通过 PR 进入评审关卡，更大的工作则写成 `intent.md`，回到第一阶段，循环由此开始自行供给后续工作。

## 10. 总结

模型和配套执行机制已经更加成熟。组织可以改造代码生产方式，也可以进一步改造整个软件开发生命周期。

这项转型继续把人的判断放在流程中心，同时考虑大型企业的治理和监管要求。

本文汇总了 Anthropic Applied AI 团队日常为客户实施的多项实践，希望它能成为一份可以直接行动的参考资料。

循环持续运行，人的判断始终位于循环之上。
