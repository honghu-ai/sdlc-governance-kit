# 项目架构

## 1. 设计依据

AI 原生 SDLC 由规划、设计、构建、测试、部署和维护组成。每个阶段提交一个可以被下一阶段读取的产物，所有提交共同形成审计记录。

本项目把治理能力分成四层。

| 层级 | 负责内容 | 主要载体 |
| --- | --- | --- |
| 产物生成 | 将原始输入整理成正式阶段产物 | `capture-intent`、`compose-spec` |
| 领域知识 | 提供品牌、合规、UX、安全和 API 约束 | `brand-guidelines`、`compliance-policy`、`security-policy` 及后续政策与标准 Skills |
| 流程编排 | 组合输入、Skills 和人工关卡 | 会话、自动任务、CI |
| 确定性控制 | 阻止危险操作和不合格变更 | Hooks、权限、分支保护、CI |

## 2. 代码库级脚手架

`sdlc-scaffold` 负责初始化和检查代码库级治理环境。它可以建立约定的父级目录、总索引、`CLAUDE.md`、`REVIEW.md` 和必要配置，也可以报告结构缺失和引用错误。

它不分配 change ID，不创建单项变更目录，也不创建任何阶段产物。重复运行不得覆盖团队已经编写的内容。

## 3. 阶段产物的创建者

| 阶段 | 正式产物 | 创建者或权威系统 |
| --- | --- | --- |
| 规划 | `intent.md` | `capture-intent` 与发起人 |
| 设计 | `spec.md` | `compose-spec`、适用政策 Skills 与产品负责人 |
| 构建 | `plan.md`、代码差异 | Claude Code 计划模式、实现会话与 Git |
| 测试 | 测试和验证证据 | 测试命令与 CI |
| 部署 | PR、评审发现、批准和部署记录 | PR 与 CI/CD 系统 |
| 维护 | 事故记录，必要时产生新的 `intent.md` | 可观测性或事故系统与 `capture-intent` |

## 4. 唯一事实来源

Markdown 产物保存在 Git。代码差异由 commit 保存，测试结果由 CI 保存，评审和批准由 PR 系统保存，部署和事故由对应平台保存。索引文件只记录必要摘要、记录 ID、URL 和 commit SHA，不复制完整外部记录。

## 5. 人工责任

Skill 可以生成草稿、约束和检查发现，不能替责任人批准结果。`brand-guidelines`、`compliance-policy` 和 `security-policy` 分别提供品牌、合规和通用安全领域内容，不能独立批准规范或例外。产品负责人批准意图与规范，工程师批准实施计划，代码负责人批准 PR，各政策负责人处理本领域冲突与例外，生产授权由组织定义的确定性关卡执行。
